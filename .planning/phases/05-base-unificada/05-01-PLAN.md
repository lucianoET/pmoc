**Função exportada `montarShell(cfg)` — pura, sem nenhum acesso ao DOM:**

Recebe um objeto de configuração com as chaves `nome` (obrigatória), `navItems` (lista, padrão vazia),
`portalLink` (booleano, padrão verdadeiro) e `versao` (texto, opcional). Retorna um objeto com duas
propriedades de texto: `topo` e `rodape`.

`topo` é a concatenação de:

1. A barra superior, com a mesma estrutura e as mesmas classes que `montarLayout()` produz hoje: um
   contêiner de classe de barra contendo o bloco de logo (ponto colorido, o texto `PMOC` e o nome do
   módulo escapado dentro do span de destaque) e o bloco à direita com — nesta ordem — o link de
   volta ao portal apontando para `/` (só quando `portalLink` for verdadeiro), o chip de usuário com
   o id `user-chip` e conteúdo inicial de travessão, e o botão secundário pequeno rotulado `Sair`
   com handler inline chamando `sair()`.

2. A faixa de abas, **apenas quando `navItems` tiver ao menos um item**. Quando a lista vier vazia, a
   faixa inteira não é emitida — é o caso do módulo Mapa, que navega por camadas na barra lateral e
   não por abas. Cada item da lista é um objeto com `id`, `icone`, `label` e `ativo`; cada um vira um
   botão de classe de aba, com a classe de estado ativo acrescentada quando `ativo` for verdadeiro,
   com o atributo `data-view` recebendo o `id` escapado, e com handler inline chamando
   `trocarView('<id>',this)`. O conteúdo visível do botão é o ícone seguido de espaço e do rótulo
   escapado.

   O atributo `data-view` é emitido para todos os módulos porque `maquinas/index.html` já o possui
   hoje e PLAT-16 proíbe perder qualquer coisa na unificação; para os demais módulos é um atributo
   de dados inerte, sem efeito visual ou funcional.

`rodape` é um elemento `footer` de classe de rodapé do shell contendo, nesta ordem (D-03): um span
com `PMOC · CMASM` seguido de travessão e do nome do módulo escapado; um span com a letra `v`
seguida da versão escapada, **emitido apenas quando `versao` for informada**; e um link para `/` com
o texto de volta ao portal.

Todo valor vindo de `cfg` — nome, id, ícone, rótulo e versão — passa por `esc()` antes de entrar no
HTML. Os valores são hoje escritos pelos próprios desenvolvedores, mas a disciplina evita reintrodução
de caminho inseguro caso algum módulo futuro passe a ler o nome do módulo do banco.

**Função exportada `aplicarShell(cfg)` — a única que toca o DOM:**

Aceita as mesmas chaves de `montarShell` mais `accent` (cor de destaque do módulo, opcional) e `alvo`
(id do elemento raiz, com padrão sendo o id do contêiner de aplicação usado por todos os módulos).
Executa, nesta ordem:

1. Define o título do documento como `PMOC ` seguido do nome do módulo.
2. Quando `accent` for informada, define a propriedade customizada de destaque no elemento raiz do
   documento — mesmo mecanismo que `montarLayout()` usa hoje.
3. Localiza o elemento raiz pelo id. Se não existir, lança erro com mensagem em português dizendo
   qual id não foi encontrado — falha alta e explícita é melhor que shell silenciosamente ausente.
4. Insere `topo` como primeiro filho do elemento raiz e `rodape` como último filho, usando inserção
   adjacente de HTML. Essa ordem preserva intacto o conteúdo que o módulo já tem dentro do contêiner
   (o miolo da página), o que permite tanto o motor de manutenção (que gera o miolo antes) quanto os
   módulos com miolo estático em HTML adotarem a mesma função.
5. Retorna o elemento raiz, para encadeamento.

Restrições inegociáveis: sem `import` de qualquer coisa; sem Shadow DOM, sem `customElements`, sem
framework, sem dependência de CDN; `montarShell` não pode referenciar `document`, `window` ou
qualquer API de navegador, porque é ela que os testes exercitam em Node.
