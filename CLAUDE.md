## Project

PMOC · CMASM — maintenance management systems (Plano de Manutenção, Operação e Controle) for the Brazilian Navy's submarine weapons center (UASG 744030). Two production apps plus a portal, all backed by one Supabase project (`pmoc`, `thoaqipyhfmromsgzmjs`, sa-east-1).

**Project language is Portuguese** — code identifiers, comments, commits, UI strings, and docs are all in Portuguese. Keep it that way.

## Commands

There is no build, no npm, no lint, no automated tests. Zero-build static site.

- **Run locally:** open any `index.html` directly in a browser, or `python -m http.server` from the repo root.
- **Deploy:** push to GitHub (`luctronics-ET/pmoc` — this is what `git remote origin` points to and what triggers the deploy; the old `pmoc-overlay` name and the `luctronicserp/pmoc` reference are stale). Vercel serves the repo statically at `https://pmoc-orcin.vercel.app` (`vercel.json` rewrites `/refrigeracao`, `/maquinas`, `/transportes`, `/eletrica`, `/fonoclama`, `/predial`, `/reparos`, `/mapa` and `/calibracao` to their `index.html`; framework "Other", no build command).
- **Database changes:** write a new numbered SQL file in `supabase/` (e.g. `10_*.sql`) and run it in the Supabase SQL editor. Migrations are **additive only — never `DROP`**; archive rows with `ativo = false` instead of deleting.
- **Testing:** manual only, checklist in `TESTES.md`. Verify against the live Supabase data (currently 171 `equipamentos`, 28 `maq_ativos`, 43 `transp_ativos`, etc.). `node --test` runs the automated gate suite (164 tests as of the Reparos module) — no framework, no `package.json`, `node:test`/`node:assert` only. To rehearse the **Máquinas migration chain** (01 → 02 → 09 → 26 → 27) on a throwaway Postgres, use `tests/fixtures/banco-teste-auth.sql`, which stubs the Supabase `auth` schema — `tests/fixtures/banco-teste.sql` is for the *locais* chain and creates `maq_ativos` as a four-column stub. Procedure in `TESTES.md`.
- **Mapa vector floor plan:** `mapa/planta-cmasm.geojson` is generated by running `node mapa/gerar-planta.mjs` by hand against a local `.osm` extract — a one-time, no-network, no-dependency conversion, not a build step. **Mapa raster tiles** (optional, `mapa/tiles/`) have their own user-run procedure in `mapa/tiles/GERAR-TILES.md` (Mapnik/`osmium` rendering chain) — explicitly **not** a deploy step and not required for the map to work offline (the vector floor plan already covers that).

## Architecture

Three independent frontend entry points sharing one Postgres backend via the Supabase JS SDK (v2, loaded from CDN — no imports/bundler):

- `/index.html` — portal (navigation hub)
- `/refrigeracao/index.html` — PMOC Refrigeração v2.8, a **single ~436 KB file** with embedded CSS + JS. HVAC inventory with the full public-contracting workflow: orçamento → execução → fiscalização → composição de pagamento (ARP items) → certificação → auditoria. QR codes, print forms, CSV export (CATMAT).
- `/maquinas/index.html` + `/maquinas/app.js` — PMOC Máquinas v1.0. Hour-meter-based maintenance of cutting equipment: plans per `tipo_modelo`, automatic stock decrement, fuel tracking, depreciation, procurement shopping-list CSV.
- `/reparos/index.html` + `/reparos/app.js` — PMOC Reparos v1.0 (18/08/2026). Symptom → probable-cause catalogue keyed on machine **model** (`rep_modelos`), not on asset or organisation, with the parts (`maq_materiais`) and labour services (`rep_servicos`) each repair consumes. Complements Máquinas: there the trigger is the hour meter (`maq_planos`, deterministic); here it is the reported symptom (probabilistic, ranked). `rep_reparos.frequencia` is incremented by the `rep_confirmar_reparo` RPC when the mechanic confirms the cause while closing a corrective OS in `maquinas/`, so the diagnosis list stops being alphabetical and starts reflecting what actually fails in this workshop. The RPC is `security invoker` and **idempotent** — a second call on the same OS raises instead of double-counting a network retry. Migrations `26_reparos_schema.sql`, `27_reparos_seed.sql` and `28_reparos_alinha_schema.sql`, all applied in production on 2026-08-18 (7 models, 25 services, 33 repairs, all 28 `maq_ativos` back-filled with `modelo_id`). **Migration 28 exists because the `rep_*` tables had been created from a draft schema before 26 ran: `create table if not exists` is a no-op on an existing table, so 26's correct definitions were skipped silently, with no error — additive migrations guarantee a table's existence, not its shape; verify columns after applying.** `maquinas/app.js` loads the catalogue in `carregarCatalogoReparos()`, deliberately **outside** the main `Promise.all`, and only adds `reparo_id`/`sintoma_relatado` to the OS insert when a diagnosis was picked — so on a database without migration 26 the module behaves exactly as it did before. Like `/mapa` after Phase 10, the **write path has never been exercised**: `frequencia` is 0 on all 33 rows; checklist in `TESTES.md`.
- `/shared/auth.js` — reusable role-login ES module (`Auth` class), imported by all six new-generation modules (`transportes`, `eletrica`, `fonoclama`, `predial`, `mapa`, `maquinas`). `refrigeracao` stays outside this base, frozen by user decision.
- `/shared/shell.js` — reusable layout shell (`aplicarShell()`): header, tab strip (when the module has one) and footer, consumed by the same six modules above. Changing `shell.js` changes header/tabs/footer for all six at once.
- `/shared/tema.js` — single light/dark theme implementation (detection, closed-list validation, application, toggling and persistence) for all 7 surfaces (the 6 modules + portal). Consumed by the 6 modules through `aplicarShell()` → `iniciarTema()`, and by the portal directly (it doesn't load the shared shell). Changing it changes the theme mechanism for all 7 surfaces at once. Its two pure functions (`normalizarTema`, `proximoTema`) are deliberately free of any browser API, kept testable in Node — the same pure-core/DOM-applier split `shell.js` already uses between `montarShell()`/`aplicarShell()`.
- `/mapa/` — PMOC Mapa operacional (Phase 10), no longer a demo-data viewer. `mapa/xmap.js` is the untouched Leaflet component (locked, no edits allowed — see Phase 10 decisions below); `mapa/mapa-dados.js` is the **single door to Supabase** inside `mapa/` — every read and write in the module goes through it (`carregarAreas`, `carregarAtivosDoModulo`, `posicionarAtivos`, `salvarZona`/`atualizarZona`, `salvarPosicaoAtivo`), enforced by a permanent gate (`tests/mapa-camadas.test.js`) so no query is ever allowed to appear anywhere else under `mapa/`; `mapa/mapa-geometria.js` is the pure core (same pure-core/DOM-applier split as `shared/tema.js`) — geodesic area, machine-compatibility rule, closed-list terrain vocabulary, geographic envelope, two-layer position resolution, module deep-link builder — free of any browser API, testable in Node; `mapa/mapa-editor.js` layers two edit modes (draw a service zone; position/reposition an asset) on top of the existing map instance, each scoped to the role list that mirrors the write policy of the table it touches; `mapa/planta-cmasm.geojson` is a static vector floor-plan of the CMASM area (117 features, 171 KB, ODbL-attributed, converted once from a local `.osm` extract by `mapa/gerar-planta.mjs`) that draws with the network off; `mapa/tiles/` is the destination for optional local raster tiles (`{z}/{x}/{y}.png`), empty today (only `.gitkeep`), with its own user-run procedure documented in `mapa/tiles/GERAR-TILES.md` — not a deploy step, not a blocker.

**Theme convention (locked, Phase 6):** `data-theme="claro"|"escuro"` attribute on the root element, `localStorage` key `pmoc-tema` (values in Portuguese, matching the rest of the codebase). Dark stays the default in `shared/pmoc.css:root` (unchanged, byte-identical); light is an additive `[data-theme="claro"]` block overriding only the neutral/semantic tokens. Three deliberate exceptions: the portal duplicates the same token *values* inline (it never loads `shared/pmoc.css`) but reuses `shared/tema.js` for all logic — no theme code is duplicated; `mapa/xmap.css` (the Leaflet skin, its own `--xm-*` token system) stays dark-only by decision, out of scope; and `/calibracao` (D-05) is a standalone legacy app outside this convention entirely — it ships its own toggle on `localStorage['cmasm_erp_theme']` with `dark`/`light` values, so switching the platform theme does not affect it. `refrigeracao` is outside as well, frozen (D-04). A classic (non-module, no external `src`) anti-FOUC script — inline, byte-identical — is replicated in the `<head>` of all 7 surfaces, immediately after the `theme-color` meta tag, applying the saved/detected theme before first paint; ES modules are deferred and would repaint too late, reintroducing the flash. `tests/tema-superficies.test.js` enforces that the 7 copies stay identical — don't fix one and forget the other six.

**State pattern (both apps):** global UPPER_CASE arrays (`ATIVOS`, `OS_LIST`, `MATERIAIS`, `PLANOS`, …) populated by `carregarTudo()` (parallel `Promise.all` Supabase queries), then `render*()` functions rebuild DOM sections via template literals. Every save re-runs `carregarTudo()` — no optimistic updates, no partial refresh. Modals drive all CRUD; inline `onclick="fn(${id})"` handlers are the norm.

**Auth & security:** login is by cargo button + password — emails (`direcao@cmasm.local`, etc.) are internal and never shown to users. Roles: `admin`, `gestor`, `tecnico`, `observador` (read-only, no password). Role lives in the `usuarios` table. The Supabase `anon key` is hardcoded in the frontends **by design** — real access control is RLS policies in Postgres; any client-side permission check is UX only. New cargos: edit the `CARGOS` array at the top of `maquinas/app.js`. `mapa/mapa-dados.js` exports **two separate role lists**, deliberately different, because each screen mirrors the write policy of the table it grants — not a UI preference: `CARGOS_ZONA` (`admin`, `gestor`, defined in `mapa/mapa-editor.js`) mirrors `maq_areas`'s write policy 1:1 (migration 12, `role in ('admin','gestor')`); `CARGOS_POSICAO` (`admin`, `gestor`, `tecnico`, exported from `mapa/mapa-dados.js`) is a **deliberate subset** of what the asset tables' policy would actually accept (`to authenticated using (true)`, no `role in (...)` restriction) — the client list is narrower than the database would allow, by design, not a mirror. A permanent test compares each list against the real policy it claims to reflect (`tests/mapa-editor.test.js`, `tests/mapa-posicionamento.test.js`).

**OS lifecycle (Máquinas, 18/08/2026):** `maq_os.status` always accepted the closed list `pendente`/`em_andamento`/`concluida`/`cancelada` (migration 01), but the app hardcoded `'concluida'` on insert — every OS was born finished, and stock was debited at creation time. The workshop flow (18/08/2026, evening) is **Aberta (reception) → Delineamento (diagnosis; parts+services listed; `delineado_por`/`delineado_em` recorded on closing it) → Espera (waiting for parts or a technician) → Em execução → Concluída** — `supabase/31_maquinas_os_fluxo.sql` (**not yet applied**) widens the `maq_os_status_check` closed list with the two new states (first constraint *swap* in the project — nothing dropped, the list only grows; until it runs, advancing into the two new states fails with the raw check-constraint alert, everything else works) and adds the two delineation columns. **Stock is debited when execution STARTS, never on creation or waiting** — an OS on the shelf that already consumed a part would lie about the inventory. Every path into execution (advance from the list, create-as-executing, status change in the detail modal, concluding an old OS that never executed) calls the same `baixarPecasDaOS()`, which is **idempotent**: it checks `maq_estoque_movimentos` for an existing 'saida' with that `os_id` — the stock's own record, not a parallel flag — so concluding an OS whose parts already left the shelf does not debit twice. The OS list has a **Material** column (⚠ falta N / EM ESTOQUE) plus a `filtro-os` select whose `falta` option isolates OS blocked on parts (`faltasDaOS()` — meaningless once execution started, so it returns empty then). `supabase/29_maquinas_os_itens.sql` (additive, **applied in production on 2026-08-18** and verified against the live database: 8 columns, the `(os_id, plano_id)` unique, both indexes, RLS on with its two policies, `maq_os` untouched) adds `maq_os_itens` so one OS can carry several maintenance items — `maq_os.plano_id` stays populated with the first item, so nothing written before it breaks. `carregarItensOS()` sits **outside** the main `Promise.all` for the same reason `carregarCatalogoReparos()` does: without migration 29 the list stays empty and `itensDaOS()` falls back to the single `plano_id`, exactly as the module behaved before. Gate: `tests/os-ciclo-vida-maquinas.test.js`.

**OS costs (Máquinas, 18/08/2026):** `maq_os.custo_pecas` and `custo_mo` used to be numbers typed into the form — nobody knew which parts or how many hours produced them. `supabase/30_maquinas_os_custos.sql` (additive, **applied in production on 2026-08-18** and verified against the live database: all three tables with the exact shape, 7 constraints on `maq_os_materiais` including the `(os_id, material_id)` unique, 6 on `maq_os_servicos` including the identification check, RLS on all three with its 6 policies, `valor_hora_padrao` still null) adds `maq_os_materiais` and `maq_os_servicos` (the two lists an OS carries) plus `maq_config` (one row per key; today only `valor_hora_padrao`). Cost is now derived: parts = Σ quantity × unit price, labour = Σ hours × hourly rate, and both fields are read-only on screen. **Unit values are frozen on the row** (`preco_unit`, `valor_hora`), not just referenced — a catalogue reprice in September must not change an OS closed in August; the FK says where it came from, the value column says what it cost. `pecasPrevistasDaOS()` merges plan and diagnosis into **one** list keyed by material, so a part appearing in both is debited once, not twice; `baixarPecasDaOS(osId, pecas, reparo)` takes that resolved list. Concluding an OS debits its own `maq_os_materiais` rows, falling back to the resolved prediction only for OS created before migration 30. The hourly rate is **a single module-wide value, deliberately empty** — inventing one would produce false labour cost on every OS; while empty, labour is zero and the screen says why. Gate: `tests/os-custos-maquinas.test.js`.

**Database:** machine tables use the `maq_` prefix; refrigeration tables are unprefixed (`equipamentos`, `arp_itens`, `os_contratacao`, `os_composicao`, …); `usuarios` is shared. Maintenance plans link to assets by `tipo_modelo` (each model has its own manual), not by FK to a specific asset. **Phase 10 (`supabase/25_mapa_geometria_posicao.sql`, additive):** `maq_areas` gains `geom jsonb` (polygon vertices) plus three closed-list terrain attributes (`flora`, `inclinacao`, `limpeza`); `cmasm_locais` and the five asset tables (`maq_ativos`, `transp_ativos`, `elet_ativos`, `fono_ativos`, `equipamentos`) gain nullable `lat`/`lon`, in a deliberate **two-layer position architecture** — position inherited from the building/room in `cmasm_locais`, overridable by a position of the asset's own row — because the existing `local_id` link only places an asset in the org tree, not in space. All twelve position columns share two database-level integrity checks per table: a geographic-envelope check (`-23.2/-22.5/-43.5/-42.7`, one combined `AND` constraint so a swapped lat/lon pair is caught too) and a complete-pair check (never half a coordinate) — both enforced in Postgres regardless of what client-side validation does. **Migration 25 ran in production on 2026-08-18** and was verified against the live database: 16 columns (12 position + `geom` + the three terrain attributes) and 15 checks (6 tables x envelope + complete-pair, plus the three closed lists on `maq_areas`) are in place. What is still untested end-to-end is the **write** path — every position column is `null` and `maq_areas` has zero rows with geometry, so no `salvarZona`/`salvarPosicaoAtivo` call has ever reached the database from the app.

## Conventions

- Globals `UPPER_CASE`, functions `camelCase`, private helpers `_prefixed`, HTML ids `kebab-case`.
- Section comments as `// ── nome ──`.
- Supabase error handling idiom: `const { error } = await supa.from(...)…; if(error){ alert('Erro: '+error.message); return }`.
- Detailed codebase analysis lives in `.planning/codebase/` (ARCHITECTURE, STACK, CONVENTIONS, TESTING, CONCERNS, INTEGRATIONS, STRUCTURE) — read those before large changes.

Gate: `tests/mapa-base-offline.test.js` (scoped to the satellite construction region of `mapa/xmap.js`, not the whole file, because the local-tile class legitimately appears elsewhere in the same file for the other basemap).

Not in the legacy app; when it arrives, it should derive from real execution (`maq_operacoes.horas_utilizadas`/`area_executada_m2`), not an arbitrary constant. Gate: `tests/mapa-decisoes.test.js` (no file under `mapa/` may reference those two columns).
