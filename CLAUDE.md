## Commands

There is no build, no npm, no lint, no automated tests. Zero-build static site.

- **Run locally:** open any `index.html` directly in a browser, or `python -m http.server` from the repo root.
- **Deploy:** push to GitHub (`luctronics-ET/pmoc` — this is what `git remote origin` points to and what triggers the deploy; the old `pmoc-overlay` name and the `luctronicserp/pmoc` reference are stale). Vercel serves the repo statically at `https://pmoc-orcin.vercel.app` (`vercel.json` rewrites `/refrigeracao`, `/maquinas`, `/transportes`, `/eletrica` and `/fonoclama` to their `index.html`; framework "Other", no build command).
- **Database changes:** write a new numbered SQL file in `supabase/` (e.g. `10_*.sql`) and run it in the Supabase SQL editor. Migrations are **additive only — never `DROP`**; archive rows with `ativo = false` instead of deleting.
- **Testing:** manual only, checklist in `TESTES.md`. Verify against the live Supabase data (currently 171 `equipamentos`, 28 `maq_ativos`, 43 `transp_ativos`, etc.). `node --test` runs the automated gate suite (135 tests as of Phase 10) — no framework, no `package.json`, `node:test`/`node:assert` only.
- **Mapa vector floor plan:** `mapa/planta-cmasm.geojson` is generated by running `node mapa/gerar-planta.mjs` by hand against a local `.osm` extract — a one-time, no-network, no-dependency conversion, not a build step. **Mapa raster tiles** (optional, `mapa/tiles/`) have their own user-run procedure in `mapa/tiles/GERAR-TILES.md` (Mapnik/`osmium` rendering chain) — explicitly **not** a deploy step and not required for the map to work offline (the vector floor plan already covers that).

## Architecture

Three independent frontend entry points sharing one Postgres backend via the Supabase JS SDK (v2, loaded from CDN — no imports/bundler):

- `/index.html` — portal (navigation hub)
- `/refrigeracao/index.html` — PMOC Refrigeração v2.8, a **single ~436 KB file** with embedded CSS + JS. HVAC inventory with the full public-contracting workflow: orçamento → execução → fiscalização → composição de pagamento (ARP items) → certificação → auditoria. QR codes, print forms, CSV export (CATMAT).
- `/maquinas/index.html` + `/maquinas/app.js` — PMOC Máquinas v1.0. Hour-meter-based maintenance of cutting equipment: plans per `tipo_modelo`, automatic stock decrement, fuel tracking, depreciation, procurement shopping-list CSV.
- `/shared/auth.js` — reusable role-login ES module (`Auth` class), imported by all six new-generation modules (`transportes`, `eletrica`, `fonoclama`, `predial`, `mapa`, `maquinas`). `refrigeracao` stays outside this base, frozen by user decision.
- `/shared/shell.js` — reusable layout shell (`aplicarShell()`): header, tab strip (when the module has one) and footer, consumed by the same six modules above. Changing `shell.js` changes header/tabs/footer for all six at once.
- `/shared/tema.js` — single light/dark theme implementation (detection, closed-list validation, application, toggling and persistence) for all 7 surfaces (the 6 modules + portal). Consumed by the 6 modules through `aplicarShell()` → `iniciarTema()`, and by the portal directly (it doesn't load the shared shell). Changing it changes the theme mechanism for all 7 surfaces at once. Its two pure functions (`normalizarTema`, `proximoTema`) are deliberately free of any browser API, kept testable in Node — the same pure-core/DOM-applier split `shell.js` already uses between `montarShell()`/`aplicarShell()`.
- `/mapa/` — PMOC Mapa operacional (Phase 10), no longer a demo-data viewer. `mapa/xmap.js` is the untouched Leaflet component (locked, no edits allowed — see Phase 10 decisions below); `mapa/mapa-dados.js` is the **single door to Supabase** inside `mapa/` — every read and write in the module goes through it (`carregarAreas`, `carregarAtivosDoModulo`, `posicionarAtivos`, `salvarZona`/`atualizarZona`, `salvarPosicaoAtivo`), enforced by a permanent gate (`tests/mapa-camadas.test.js`) so no query is ever allowed to appear anywhere else under `mapa/`; `mapa/mapa-geometria.js` is the pure core (same pure-core/DOM-applier split as `shared/tema.js`) — geodesic area, machine-compatibility rule, closed-list terrain vocabulary, geographic envelope, two-layer position resolution, module deep-link builder — free of any browser API, testable in Node; `mapa/mapa-editor.js` layers two edit modes (draw a service zone; position/reposition an asset) on top of the existing map instance, each scoped to the role list that mirrors the write policy of the table it touches; `mapa/planta-cmasm.geojson` is a static vector floor-plan of the CMASM area (117 features, 171 KB, ODbL-attributed, converted once from a local `.osm` extract by `mapa/gerar-planta.mjs`) that draws with the network off; `mapa/tiles/` is the destination for optional local raster tiles (`{z}/{x}/{y}.png`), empty today (only `.gitkeep`), with its own user-run procedure documented in `mapa/tiles/GERAR-TILES.md` — not a deploy step, not a blocker.

**Theme convention (locked, Phase 6):** `data-theme="claro"|"escuro"` attribute on the root element, `localStorage` key `pmoc-tema` (values in Portuguese, matching the rest of the codebase). Dark stays the default in `shared/pmoc.css:root` (unchanged, byte-identical); light is an additive `[data-theme="claro"]` block overriding only the neutral/semantic tokens. Three deliberate exceptions: the portal duplicates the same token *values* inline (it never loads `shared/pmoc.css`) but reuses `shared/tema.js` for all logic — no theme code is duplicated; `mapa/xmap.css` (the Leaflet skin, its own `--xm-*` token system) stays dark-only by decision, out of scope; and `/calibracao` (D-05) is a standalone legacy app outside this convention entirely — it ships its own toggle on `localStorage['cmasm_erp_theme']` with `dark`/`light` values, so switching the platform theme does not affect it. `refrigeracao` is outside as well, frozen (D-04). A classic (non-module, no external `src`) anti-FOUC script — inline, byte-identical — is replicated in the `<head>` of all 7 surfaces, immediately after the `theme-color` meta tag, applying the saved/detected theme before first paint; ES modules are deferred and would repaint too late, reintroducing the flash. `tests/tema-superficies.test.js` enforces that the 7 copies stay identical — don't fix one and forget the other six.

**State pattern (both apps):** global UPPER_CASE arrays (`ATIVOS`, `OS_LIST`, `MATERIAIS`, `PLANOS`, …) populated by `carregarTudo()` (parallel `Promise.all` Supabase queries), then `render*()` functions rebuild DOM sections via template literals. Every save re-runs `carregarTudo()` — no optimistic updates, no partial refresh. Modals drive all CRUD; inline `onclick="fn(${id})"` handlers are the norm.

**Auth & security:** login is by cargo button + password — emails (`direcao@cmasm.local`, etc.) are internal and never shown to users. Roles: `admin`, `gestor`, `tecnico`, `observador` (read-only, no password). Role lives in the `usuarios` table. The Supabase `anon key` is hardcoded in the frontends **by design** — real access control is RLS policies in Postgres; any client-side permission check is UX only. New cargos: edit the `CARGOS` array at the top of `maquinas/app.js`. `mapa/mapa-dados.js` exports **two separate role lists**, deliberately different, because each screen mirrors the write policy of the table it grants — not a UI preference: `CARGOS_ZONA` (`admin`, `gestor`, defined in `mapa/mapa-editor.js`) mirrors `maq_areas`'s write policy 1:1 (migration 12, `role in ('admin','gestor')`); `CARGOS_POSICAO` (`admin`, `gestor`, `tecnico`, exported from `mapa/mapa-dados.js`) is a **deliberate subset** of what the asset tables' policy would actually accept (`to authenticated using (true)`, no `role in (...)` restriction) — the client list is narrower than the database would allow, by design, not a mirror. A permanent test compares each list against the real policy it claims to reflect (`tests/mapa-editor.test.js`, `tests/mapa-posicionamento.test.js`).

**Database:** machine tables use the `maq_` prefix; refrigeration tables are unprefixed (`equipamentos`, `arp_itens`, `os_contratacao`, `os_composicao`, …); `usuarios` is shared. Maintenance plans link to assets by `tipo_modelo` (each model has its own manual), not by FK to a specific asset. **Phase 10 (`supabase/25_mapa_geometria_posicao.sql`, additive):** `maq_areas` gains `geom jsonb` (polygon vertices) plus three closed-list terrain attributes (`flora`, `inclinacao`, `limpeza`); `cmasm_locais` and the five asset tables (`maq_ativos`, `transp_ativos`, `elet_ativos`, `fono_ativos`, `equipamentos`) gain nullable `lat`/`lon`, in a deliberate **two-layer position architecture** — position inherited from the building/room in `cmasm_locais`, overridable by a position of the asset's own row — because the existing `local_id` link only places an asset in the org tree, not in space. All twelve position columns share two database-level integrity checks per table: a geographic-envelope check (`-23.2/-22.5/-43.5/-42.7`, one combined `AND` constraint so a swapped lat/lon pair is caught too) and a complete-pair check (never half a coordinate) — both enforced in Postgres regardless of what client-side validation does. **Migration 25 has not yet been run in production** — it is a `user_setup` step for the SQL Editor; every write path built in Phase 10 is written against this schema but untested end-to-end until it runs.

## Decisões travadas — Phase 10 (mapa operacional)

Each has a permanent automated gate — a future phase contradicting one of these fails `node --test` before reaching human review:

- **D-01** — the `aguada` layer stays **out** of the "camadas leem do Supabase" requirement (PLAT-17), deferred to Phase 11. It has no table in pmoc — it's an autonomous external system (FastAPI + SQLite, fed by MQTT). Gate: `tests/mapa-decisoes.test.js`.
- **D-02** — the satellite basemap stays **online-only**, no local tile cache, by user decision. Gate: `tests/mapa-base-offline.test.js` (scoped to the satellite construction region of `mapa/xmap.js`, not the whole file, because the local-tile class legitimately appears elsewhere in the same file for the other basemap).
- **D-03** — service zones live in `maq_areas`, deliberately **outside** the `cmasm_locais` tree — they're auxiliary and temporary, not permanent locations. Not gated by a dedicated test; documented here so a future phase doesn't "reorganize" them into the locations tree.
- **D-04** — time/cost estimate per zone is **out of scope**. Not in the legacy app; when it arrives, it should derive from real execution (`maq_operacoes.horas_utilizadas`/`area_executada_m2`), not an arbitrary constant. Gate: `tests/mapa-decisoes.test.js` (no file under `mapa/` may reference those two columns).
