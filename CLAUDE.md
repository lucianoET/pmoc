## Commands

There is no build, no npm, no lint, no automated tests. Zero-build static site.

- **Run locally:** serve the repo over HTTP (`python -m http.server` from the repo root) — opening an `index.html` directly from the filesystem (`file://`) no longer works in any module (D-td4-07, 260821-td4): every module references its own assets by root-absolute path (`/refrigeracao/qrcode.js`, `/mapa/xmap.js`, …) so `qrcode.js` resolves on the rewrite-without-trailing-slash route Vercel actually serves in production, and a root-absolute path has no meaning under `file://`. This is the cost of the rule, paid by all 9 modules since it started, not a side effect of this fix.
- **Deploy:** push to GitHub (`luctronics-ET/pmoc` — this is what `git remote origin` points to and what triggers the deploy; the old `pmoc-overlay` name and the `luctronicserp/pmoc` reference are stale). Vercel serves the repo statically at `https://pmoc-orcin.vercel.app` (`vercel.json` rewrites `/refrigeracao`, `/maquinas`, `/transportes`, `/eletrica`, `/fonoclama`, `/predial`, `/reparos`, `/mapa` and `/calibracao` to their `index.html`; framework "Other", no build command).
- **Database changes:** write a new numbered SQL file in `supabase/` (e.g. `10_*.sql`) and run it in the Supabase SQL editor. Migrations are **additive only — never `DROP`**; archive rows with `ativo = false` instead of deleting.
- **Testing:** manual only, checklist in `TESTES.md`. Verify against the live Supabase data (currently 171 `equipamentos`, 28 `maq_ativos`, 43 `transp_ativos`, etc.). `node --test` runs the automated gate suite (164 tests as of the Reparos module) — no framework, no `package.json`, `node:test`/`node:assert` only. To rehearse the **Máquinas migration chain** (01 → 02 → 09 → 26 → 27) on a throwaway Postgres, use `tests/fixtures/banco-teste-auth.sql`, which stubs the Supabase `auth` schema — `tests/fixtures/banco-teste.sql` is for the *locais* chain and creates `maq_ativos` as a four-column stub. Procedure in `TESTES.md`.
- **Mapa vector floor plan:** `mapa/planta-cmasm.geojson` is generated by running `node mapa/gerar-planta.mjs` by hand against a local `.osm` extract — a one-time, no-network, no-dependency conversion, not a build step. **Mapa raster tiles** (optional, `mapa/tiles/`) have their own user-run procedure in `mapa/tiles/GERAR-TILES.md` (Mapnik/`osmium` rendering chain) — explicitly **not** a deploy step and not required for the map to work offline (the vector floor plan already covers that).

## Architecture

Three independent frontend entry points sharing one Postgres backend via the Supabase JS SDK (v2, loaded from CDN — no imports/bundler):

- `/index.html` — portal (navigation hub)
- `/refrigeracao/index.html` — PMOC Refrigeração v2.8, a **single ~436 KB file** with embedded CSS + JS. HVAC inventory with the full public-contracting workflow: orçamento → execução → fiscalização → composição de pagamento (ARP items) → certificação → auditoria. QR codes, print forms, CSV export (CATMAT).
- `/maquinas/index.html` + `/maquinas/app.js` — PMOC Máquinas v1.0. Hour-meter-based maintenance of cutting equipment: plans per `tipo_modelo`, automatic stock decrement, fuel tracking, depreciation, procurement shopping-list CSV.
- `/reparos/index.html` + `/reparos/app.js` — PMOC Reparos v1.0 (18/08/2026). Symptom → probable-cause catalogue keyed on machine **model** (`rep_modelos`), not on asset or organisation, with the parts (`maq_materiais`) and labour services (`rep_servicos`) each repair consumes. Complements Máquinas: there the trigger is the hour meter (`maq_planos`, deterministic); here it is the reported symptom (probabilistic, ranked). `rep_reparos.frequencia` is incremented by the `rep_confirmar_reparo` RPC when the mechanic confirms the cause while closing a corrective OS in `maquinas/`, so the diagnosis list stops being alphabetical and starts reflecting what actually fails in this workshop. The RPC is `security invoker` and **idempotent** — a second call on the same OS raises instead of double-counting a network retry. Migrations `26_reparos_schema.sql`, `27_reparos_seed.sql` and `28_reparos_alinha_schema.sql`, all applied in production on 2026-08-18 (7 models, 25 services, 33 repairs, all 28 `maq_ativos` back-filled with `modelo_id`). **Migration 28 exists because the `rep_*` tables had been created from a draft schema before 26 ran: `create table if not exists` is a no-op on an existing table, so 26's correct definitions were skipped silently, with no error — additive migrations guarantee a table's existence, not its shape; verify columns after applying.** `maquinas/app.js` loads the catalogue in `carregarCatalogoReparos()`, deliberately **outside** the main `Promise.all`, and only adds `reparo_id`/`sintoma_relatado` to the OS insert when a diagnosis was picked — so on a database without migration 26 the module behaves exactly as it did before. Like `/mapa` after Phase 10, the **write path has never been exercised**: `frequencia` is 0 on all 33 rows; checklist in `TESTES.md`.
- `/shared/auth.js` — reusable role-login ES module (`Auth` class), imported by all six new-generation modules (`transportes`, `eletrica`, `fonoclama`, `predial`, `mapa`, `maquinas`). `refrigeracao` stays outside this base, frozen by user decision.
- `/shared/shell.js` — reusable layout shell (`aplicarShell()`): header, tab strip (when the module has one) and footer, consumed by the same six modules above. Changing `shell.js` changes header/tabs/footer for all six at once.
- `/shared/tema.js` — single light/dark theme implementation (detection, closed-list validation, application, toggling and persistence) for all 7 surfaces (the 6 modules + portal). Consumed by the 6 modules through `aplicarShell()` → `iniciarTema()`, and by the portal directly (it doesn't load the shared shell). Changing it changes the theme mechanism for all 7 surfaces at once. Its two pure functions (`normalizarTema`, `proximoTema`) are deliberately free of any browser API, kept testable in Node — the same pure-core/DOM-applier split `shell.js` already uses between `montarShell()`/`aplicarShell()`.
- `/mapa/` — PMOC Mapa operacional (Phase 10), no longer a demo-data viewer. `mapa/mapa-exportar.js` (GeoJSON out, pure core + DOM edge) and `mapa/mapa-planta.js` (georeferenced reference floor plan, tab-only) are the two files ported in function from the `cmasm-mapa-v2` prototype. `mapa/xmap.js` is the untouched Leaflet component (locked, no edits allowed — see Phase 10 decisions below); `mapa/mapa-dados.js` is the **single door to Supabase** inside `mapa/` — every read and write in the module goes through it (`carregarAreas`, `carregarAtivosDoModulo`, `posicionarAtivos`, `salvarZona`/`atualizarZona`, `salvarPosicaoAtivo`), enforced by a permanent gate (`tests/mapa-camadas.test.js`) so no query is ever allowed to appear anywhere else under `mapa/`; `mapa/mapa-geometria.js` is the pure core (same pure-core/DOM-applier split as `shared/tema.js`) — geodesic area, machine-compatibility rule, closed-list terrain vocabulary, geographic envelope, two-layer position resolution, module deep-link builder — free of any browser API, testable in Node; `mapa/xmap-layers-ativos.js` is the **generic** asset layer — one registration function driven by `CONFIG_POR_MODULO`, not three copies of `xmap-layers-eletrica.js`; `mapa/mapa-editor.js` layers two edit modes (draw a service zone; position/reposition an asset **or building**) on top of the existing map instance, each scoped to the role list that mirrors the write policy of the table it touches; `mapa/planta-cmasm.geojson` is a static vector floor-plan of the CMASM area (117 features, 171 KB, ODbL-attributed, converted once from a local `.osm` extract by `mapa/gerar-planta.mjs`) that draws with the network off; `mapa/tiles/` is the destination for optional local raster tiles (`{z}/{x}/{y}.png`), empty today (only `.gitkeep`), with its own user-run procedure documented in `mapa/tiles/GERAR-TILES.md` — not a deploy step, not a blocker.
- `/calibracao/` — CMASM Controle de Calibração, app legado independente: um único `index.html` de ~860 KB com React 18 **embutido** (o SheetJS **não** é embutido, ao contrário do que esta nota afirmou até 02/09/2026: é buscado em `cdnjs` por `ensureXLSX()` só na hora de exportar, então a exportação para Excel nunca funcionou offline), sidebar e tema próprios, 11 páginas (dashboard, equipamentos, pedidos de serviço, laboratórios, certificados, relatório, lotes, catálogo de preços, saldo da ATA, dados, ajuda). **Migrado do localStorage para o Supabase em 18/08/2026** (migrações 35 e 36): era o único módulo da plataforma sem banco — os 38 instrumentos, 8 laboratórios, 12 PS, 2 lotes e o catálogo viviam em `localStorage['cmasm_erp_state_v1']`, de modo que limpar o cache apagava o controle de calibração e cada computador via um dado diferente. `useStore()` continua sendo a **costura única**: carrega as cinco tabelas `cal_*` em paralelo e cada mutator grava a própria linha — nunca o blob, senão dois usuários simultâneos se sobrescrevem em silêncio. Fora de `useStore()` e dos helpers de borda o React é intocado, e por isso a gravação é **otimista** (a tela já mostrou a mudança; erro alerta e recarrega): tornar os mutators assíncronos obrigaria a reescrever as 11 páginas. Duas fronteiras, cada uma num lugar só: `CAMPOS_LAB`/`CAMPOS_EQ`/`CAMPOS_PS`/`CAMPOS_LOTE` traduzem o camelCase do app (`eqId`, `labId`, `cC`) para o snake_case do Postgres, e `paraISO`/`paraBR` traduzem `dd/mm/aaaa` para `date` — o gate compara os mapas coluna a coluna com a migração 35, porque **um campo fora do mapa é gravado como null sem erro nenhum**. O contador de PS deixou de ser persistido: é derivado do maior `PS-CMS-{ano}-NNN` já emitido, e `cal_ps.num` é `unique`, porque um número de sequência mantido no cliente produz PS duplicado assim que duas pessoas emitem ao mesmo tempo. `ATA_ITEMS_SEED` (35 itens da ata 00129/2025) e `ATA_INFO` **não ganharam tabela** — conferido que só aparecem em `.map()`/`.find()`, nunca em escrita. O SDK do Supabase vem de CDN, ao contrário do React e do SheetJS embutidos: o módulo passou a depender de rede de qualquer forma, então embutir o SDK não devolveria o modo offline. `calibracao/gerar-seed.mjs` gera a migração 36 a partir das constantes do próprio `index.html`, rodado à mão uma vez, como `mapa/gerar-planta.mjs` — não é passo de build. Gate: `tests/calibracao-supabase.test.js`.

**Cobertura e posicionamento do mapa (quick-260818-vxu, 18/08/2026):** the map covered 2 of the 5 asset families — 229 assets (43 `transp_ativos`, 15 `fono_ativos`, 171 `equipamentos`) had a `lat`/`lon` pair from migration 25 and no layer to appear in. `mapa/mapa-dados.js` replaced `TABELA_POR_MODULO`/`COLUNAS_POR_MODULO` with a single **`CONFIG_POR_MODULO`** because `equipamentos` shares *no* column with the other four: no `ativo`, no `codigo`, no `nome`, no `status` — its state lives in `funciona` (`OK`/`NOK`) while the column literally named `estado` holds the unit's age (`NOVA`/`SEMI`/`VELHA`). With fixed columns the only way in was an `if` for one module inside the loader, and the next odd schema would bring the second; the table's shape is now data. The module key is **`climatizacao`, never `refrigeracao`** — `tests/mobile-375.test.js` (PLAT-15) forbids naming the frozen app in `mapa/index.html`, and `MODULOS` (`mapa-geometria.js`) has no route for it, so the popup simply omits the ficha link. **Two position doors, one per layer of `resolverPosicao`:** `salvarPosicaoAtivo` (asset's own row, forbidden from touching `cmasm_locais`, D-03) and the new `salvarPosicaoLocal` (`cmasm_locais` only, touching no asset table) — the `if` choosing between them lives in the *caller* (`aoClicarParaPosicionar`), so neither function ever decides on its own which table to write. Until this task the inherited layer was dead code: there was no way to give a building a coordinate. The sidebar lists buildings **ordered by how many assets each one would light up** (counted from `NAO_LOCALIZADOS`, no extra query — an asset is only in that list if it has neither its own nor an inherited position, so its `local_id` names exactly the building that would place it), truncated at 25 with the remainder **announced**, never silently. Zones with `geom` null were unreachable (`carregarZonasEditaveis` skips fewer than 3 vertices) and drawing over one inserted a duplicate; the "Desenhar" button now **arms** the next polygon for `atualizarZona` of that row. **Prédio como polígono, zona como vegetação, controles do mapa (quick-260819-0g3, 19/08/2026):** a building was a **point** and the database showed what that cost — two of the seven zones the user had drawn in `maq_areas` were buildings ("Predio Comando", "Museu"), drawn with the service-zone tool because it was the only drawing tool that existed, which also put 2.253 m² of headquarters into the grass-cutting area. `cmasm_locais.geom` (migration 37, additive, **applied in production on 2026-08-19** and verified: column plus a shape `check`, since a brand-new column can be constrained without invalidating any existing row — `maq_areas.geom` never got that guard) holds the outline in the same `[[lat,lon], …]` shape. **`lat`/`lon` did not become optional:** `salvarGeomLocal` writes the outline and its **centroid in the same `.update(`**, because `resolverPosicao` reads the point, not the polygon — an outline without a point would silently stop lighting up every asset that inherits from that building, and that half-written state would be invisible on screen (the outline would draw, the assets would vanish). The centroid is an **area** centroid, not a vertex mean: a detailed façade with many vertices would drag a mean outside the floor plan. Two numeric corrections the test itself found: the shoelace runs with the first vertex at the origin (subtracting near-equal products at −22,84/−43,10 left noise of the same order as the building's area) and degeneracy is compared against an epsilon, never against exact zero (three collinear vertices leave a 1e-17 remainder, and the "centroid" would be noise over noise). Drawing a building is `CARGOS_POSICAO` — the list that already governed `cmasm_locais` — **not** `CARGOS_ZONA`, which mirrors `maq_areas`'s policy and has nothing to do with this write; it uses `new L.Draw.Polygon(mapa).enable()` directly, adding no toolbar to the map. Zones are now **vegetation and outdoor areas**, coloured by `flora` (the closed list of migration 25) instead of the legacy cmms-mapa dictionary (jardim/bosque/canteiro/área recreativa/horta), a vocabulary that never existed in this database — none of the seven real zones matched a key, so every one fell to the default green and the style-by-type was decorative. **Three real control overlaps, all fixed in the module's own CSS (`mapa/xmap.js` and `mapa/xmap.css` untouched):** "Editar zonas"/"Mover ativos" were Leaflet controls in `topright` — the same corner as the `.xmap-filters` panel (z-index 1000) and *below* it in the stack, so two buttons were invisible; they moved to the sidebar (`#edicao-controles`), and entering a mode now closes the sidebar instead of covering half the map you are about to click. The Layers panel also covered `#editor-painel` (z-index 900) and now steps aside while it is open, scrolling inside itself rather than growing to the footer. The basemap bar left the top centre, where it collided with ☰ Módulos on a narrow screen, for the bottom-left corner freed by hiding the active-module chips (they repeated the sidebar). **Sala herda a posição do prédio (quick-260819-23e, 19/08/2026):** positioning buildings lit up **nothing**, and the database said why: **175 of the 190 assets point at a `sala`**, and inheritance looked only at the asset's direct `local_id`. The 132 active salas are *all* children of an `edificacao` — the tree is exactly two levels deep (sala → prédio → OM). Inheritance now climbs `parent_id`: `localAscendente` (pure core) walks up with a **cycle guard**, because `parent_id` carries no acyclicity constraint in Postgres and a circular registry would freeze the tab with no error at all. Two climbs, two criteria: `localComPosicao` (where the coordinate comes from) and `localPosicionavel` (which local the user should position to light this asset up — the sala hands off to its prédio), which is what makes the sidebar's per-building count tell the truth. `carregarLocaisComPosicao` became **`carregarArvoreDeLocais`** and stopped filtering on `lat is not null`: the middle link — the sala, which never has a coordinate — must come back, or the chain breaks exactly where it needed to climb. `sala` left the "position me" list (`TIPOS_QUE_HERDAM_POSICAO`, a closed list of what *inherits*, deliberately inverted so an unknown new tipo shows up on screen instead of vanishing from it). **The root's coordinate is not inheritable** (`TIPOS_SEM_HERANCA = ['organizacao militar']`): the CMASM row itself has `lat`/`lon`, so an unbounded climb would have positioned every asset in the base — 188 pins stacked on one point, the map claiming "all located" and the não-localizados list, which *is* the field-work backlog, emptying itself. A point at the centre of 20 hectares is the absence of a position wearing the costume of data. Popups now name the origin ("Herdada de COMANDO") instead of just "herdada"; `xmap-layers-ativos.js` gained the `esc()` it never had. **Legibilidade do mapa: pilha de marcadores, rótulos, barra lateral, painel de camadas (quick-260819-348, 19/08/2026):** with the 30 buildings positioned, the screen measured **195 markers over 51 distinct points** — the tallest stack 24 icons on the same pixel (F21 19, PAIOL 16, MK48 12) — and **12 labels, all from the OSM floor plan, none from the cadastre**. The layer toggles *worked* (turning Climatização off removed 171 markers); what did not work was seeing it. Four causes, four fixes. **`agruparPorPonto`** (pure core) groups by **exact** coordinate, because the stack comes from identical coordinates — every asset inherits its building's point — not from proximity; a proximity cluster library would move the marker somewhere it isn't, which on a maintenance map is worse than stacking. **`mapa/xmap-marcadores.js`** is one marker implementation for the three asset layers: what varies is the single-asset icon and its popup, while grouping, the count badge, the colour, the list popup and the label are shared — a fix in one of three copies would never have reached the other two. The group takes the colour of its **most severe** state (`inoperante` > `manutencao` > `standby` > `operante` > `baixado`): one broken unit among twenty working ones has to be visible from far away, and an average or majority would hide exactly what the screen exists to show; an unknown state weighs as least severe rather than faking severity. The group popup **lists** its assets, each line linking to the asset's ficha, cut at 15 with the remainder announced — grouping must not cost access to the asset. **Labels are permanent tooltips hidden by CSS below zoom 17** (`.leaflet-container:not(.zoom-detalhe) .xmap-rotulo`), one class toggled on the container by `app.js` instead of every layer listening to the map. The sidebar became collapsible `<details>` sections — seven simultaneously open blocks were a wall of text — with only *Módulos* and *Edição* open and each closed header carrying its own count. The Layers panel now **starts collapsed** behind its own Portuguese header (`#btn-camadas`), placed *outside* the panel because `xmap.js` rebuilds the panel's entire interior on every toggle and would erase anything put inside it. The map opens **framing what has a position**, with `animate: false`: Leaflet's animation runs in `requestAnimationFrame`, which does not fire while the tab is not compositing, so the animated `fitBounds` silently did nothing and the map opened at zoom 15 with the base the size of a fingernail. After: **56 markers, 66 labels, zoom 17**. `mapa/xmap.js` and `mapa/xmap.css` still untouched. Gate: `tests/mapa-legibilidade.test.js`.

**Features portadas do cmasm-mapa-v2 (quick-260819-406, 19/08/2026):** `/home/luc/DEV_reference_readonly/cmasm-mapa-v2 (2).html` is a MapLibre GL + mapbox-gl-draw prototype; `/mapa` is Leaflet with `xmap.js` locked, so what gets ported is **function, not code** — and one of them comes out better than the original. **`mapa/mapa-exportar.js`** exports positioned assets, zones and building outlines as GeoJSON from what is already in memory (no new query). Its core is the coordinate order: `geom` stores `[lat, lon]` (Leaflet's order) and RFC 7946 demands `[lon, lat]` — exporting them swapped raises no error anywhere, it just puts the CMASM in Antarctica when the file opens in QGIS, which is why that is the one thing tested by behaviour. The polygon ring is **closed on export** because Leaflet's drawing does not repeat the first vertex. **`mapa/mapa-planta.js`** is the reference floor plan: the original is an `<img>` positioned with a CSS `transform`, so it does **not** follow the map — pan and the plan stays put, which makes it useful to look at but useless to draw over. Here it is `L.imageOverlay` bound to coordinates, georeferenced by hand ("Encaixar aqui" snaps it to the current view), living in the tab only — persisting it would need a Storage bucket with its own policy. The **toast** exists for a concrete reason: the editor instructed with `alert()`, and `alert` is modal — it swallowed exactly the map click the instruction was asking for; errors and validation stay in `alert`, the project idiom, because an error must stop the user. Layer **opacity is one global slider** acting on `overlayPane`/`markerPane`/`tooltipPane` and never on `tilePane` (the point is seeing the ground *under* the data); per-layer would mean editing the panel `xmap.js` rebuilds on every toggle. Live coordinate readout plus metric scale complete the set. **Deliberately not ported:** the TOPO basemap (the basemap list lives in the locked `xmap.js`), map rotation and 3D pitch (Leaflet 1.9 does neither — it would mean replacing the component with MapLibre, the rewrite the xMap port avoided), the symbol palette that inserts free-standing elements (a pmoc asset comes from one of the five tables; an element that exists only on the map has no registry, no OS and no owner), the properties panel / element list / 3D modal (equivalents already exist; the reference's 3D modal is an empty placeholder), and the Delete shortcut (the project archives, never deletes). Gate: `tests/mapa-referencia-v2.test.js`.

**Estado ativo dos menus e ícones (quick-260819-4gq, 19/08/2026):** the screenshot the user sent showed the `☰` rendering as a **black block** — `U+2630` falls back to a symbol font not every system has, and `▤` on the Layers button had the same problem; both became inline SVG using `currentColor`. "Active" was a **1px border changing colour**: too thin to read at a glance and invisible to anyone who confuses teal with grey. Active state now carries **four signals at once**, none of which alone carries the meaning: a 4px bar on the left (drawn by `::before` so the text does not jump when it turns on), a tinted background, weight 700, and a **filled dot versus an empty ring** — the one signal that survives colour blindness. It applies to the three controls that switch something on: module, edit mode, and the floating buttons. `aria-pressed` is declared in the markup on all of them, so the screen reader gets what the CSS uses to draw. The layers panel comes from the locked `xmap.js` and marked state with a 26×14px toggle; now the **whole row** answers (tinted with a bar when on, faded when off) — CSS only. Two mistakes of mine that only the screen revealed: using `var(--text)` on that panel's labels paints dark text on a dark background in the light theme, because the panel is dark-only by decision (D-01) — fixed by using the component's own tokens (`--xm-text`, `--xm-acc`); and lowering the single label threshold from 17 to 16 produced **137 overlapping labels**, fixed not by reverting but by splitting into **two thresholds** — structure (building, zone: a few dozen, and what gives the rest meaning) from zoom 15, assets from 17, which opens the map with 21 clean labels. The group label also stopped repeating the layer name: `F21 (16)` answers where and how many; `Climatização (16)` said thirty times answers nothing. Gate: `tests/mapa-legibilidade.test.js` (extended).

**Chrome padronizado — ícones, Portal, tema no rodapé (19/08/2026):** icons in the chrome were characters — `☰`, `▤`, `☀`, plus one emoji per tab — and a character depends on the font the system happens to have: the `☰` rendered as a black block on the user's machine, and tab emoji change drawing and palette per operating system, which makes standardisation impossible and makes the icon ignore the very theme its button switches. **`shared/icones.js`** is the single set: 17 icons, stroke 2 on `viewBox 24` (Material Symbols Outlined family), every one in `currentColor`, so they inherit the surrounding text colour and answer hover/active/theme without a second rule. Pure core, no browser API; an unknown name returns **empty rather than throwing** — a missing icon is one drawing less, an exception would take down the whole header build. **Calendário de OS e vencimentos (`/refrigeracao`, quick-260831-cal, 31/08/2026):** o cronograma do PMOC v8.3 era uma **lista gerada uma vez, sem memória** — rodava o algoritmo de mobilização, imprimia, e no dia seguinte imprimia outra coisa. O que entra é um calendário: mostra o que está marcado e deixa remarcar arrastando. **Sem migração (D-cal-01)** — a data de uma OS já é `logs_manutencao.data_os`, que a lista mostra e o formulário grava desde a migração 40; remarcar é um `update` nessa coluna pela MESMA porta de escrita de sempre (`manAtualizarOS`, D-cal-02). Uma coluna `data_programada` ao lado seria a sétima migração pendente e, pior, **uma segunda fonte de verdade para "quando"**, com as duas divergindo no primeiro reagendamento feito pela tela antiga. **Duas camadas que não são a mesma coisa:** OS reais (existem, têm dono e estado) e vencimentos projetados por `nextPmoc` (derivados, nenhuma linha no banco) — a segunda desenha tracejada e **não se arrasta**, porque é recalculada e não guardada. **A camada projetada é quase toda vazia hoje e a tela diz isso (D-cal-04):** `nextPmoc` devolve `null` sem data anterior e 169 dos 171 equipamentos não têm histórico, então o calendário **conta quantos ficaram de fora** em vez de parecer um mês sem nada marcado — a mesma honestidade que o estado vazio do chip "Vencidos" já pratica. **OS em estado terminal não se move (D-cal-03):** a data de uma OS concluída é registro do que foi feito, e arrastá-la reescreveria quando o serviço aconteceu; a lista de terminais é **derivada de `FLUXO_PROPRIO`/`FLUXO_CONTRATO`/`FLUXO_LEGADO`**, nunca escrita à mão, então um fluxo novo com terminal novo passa a ser respeitado sozinho. **Um defeito que só a renderização mostrou:** `agendaTerminais` lia os fluxos por `globalThis[nome]`, e os três são `var` de topo — que num sandbox ou dentro de um `eval` de função existem como variáveis e **não** como propriedades do objeto global; a lista voltava só com `CANCELADA` e uma OS **concluída ficava arrastável**, em silêncio. Passou a referência direta com guarda `typeof`. O calendário vive na página PMOC **atrás de um `seg-toggle`** (`Lista | Calendário`), não numa sexta aba: dois gates afirmam exatamente cinco `.nav-btn`, e um calendário de manutenção programada *é* a página do PMOC vista por outro eixo — o mesmo dado ordenado por data em vez de por equipamento; trocar de vista **esconde os chips**, que filtram a lista por equipamento e no calendário estariam mentindo sobre o que se vê. **Zero CSS novo fora do `@media`**: a folha de celular é comparada byte a byte com um fixture, e o calendário é feature nova nas duas larguras — a grade mora dentro do `@media` de computador (onde ela só existe mesmo) e a aparência no celular vem de estilo inline mais `.ds`/`.ds-title`, que já existiam. `agendaChave` monta a chave ISO **local, nunca por `toISOString()`**: a conversão para UTC empurraria para o dia anterior tudo antes das 21h no nosso fuso, e uma OS marcada para o dia 5 apareceria no dia 4 só para quem abrisse a tela de manhã. No celular não há arrastar (o DnD do HTML5 não dispara em toque sem polyfill, e polyfill é dependência nova) — remarcar ali é abrir a OS e usar "Corrigir", que já tem campo de data; a consequência fica registrada: no computador reagendar exige `manPode('abrir')` (inclui técnico), pelo caminho da OS exige `podeEditarCadastro()` (admin/gestor), porque aquele formulário corrige muito mais que a data. **Planilha do inventário — exportar e importar (Refrigeração, 22/08/2026):** the 171 equipment records could only be edited **one at a time**, through a 22-field drawer form — no way to fix thirty patrimônio numbers in one sitting, no way to send the list to whoever does the field survey and get back what was checked. The user asked for export/import and chose, among three modes, the most dangerous one: import **updates, creates AND archives by absence** — a row missing from the spreadsheet takes the equipment out of the active inventory. I recommended against it, in writing; the user chose it anyway. The plan implements all three, unreduced — the work is making the mode survivable, not refusing it. CSV, not XLSX (`Blob`/`URL.createObjectURL` out, `FileReader` in; UTF-8 with BOM, `;` separator — what Excel pt-BR opens with no import step), zero build, zero new dependency. **Two structural guards make the dangerous mode survivable.** First, **the exported scope is derived from content, never from screen state**: the CSV's first line declares `escopo=completo|parcial` — true iff the exported set contains every `instalado` id in `DATA` at export time, computed by set membership, never by reading the active filter chip. A filtered export (e.g. "Área Vermelha") is structurally `parcial` and a `parcial` file **never** computes an archive list, no matter how many rows are absent — this makes the most likely accident (filter it, export it, reimport it, and everything outside the filter vanishes) structurally impossible rather than merely gated. Second, **a scale guard**: `max(5, ceil(10% of instalados))` — today `max(5, 18)`. This database has never recorded an archive (0 of 171), so a first batch above the ceiling is, by evidence, far more likely to be a spreadsheet accident than a real bulk removal; below the ceiling still requires passing the nominal confirmation screen. Three preconditions gate archiving as a whole, all must hold: `escopo=completo` on the file, zero rejected rows (D-5hy-11: a file with any rejected row — bad id, ambiguous date, out-of-list criticidade — archives nothing, though its valid update/create rows still apply), and the file's declared `instalados=N` matching `DATA`'s current installed count (catches the file being edited/truncated after export, or the inventory growing since). **Archiving is always and only the `removido` situação — never `baixado`.** Patrimonial write-off (`baixado`) stays exclusively reachable through the OS de movimentação conference, admin-gated (D-uyz-07) — a forgotten spreadsheet row can never trigger a formal write-off act. This is a permanent gate: within the spreadsheet's pure-core section, the terminal word of `SITUACAO_ORDEM` may not appear anywhere (word-boundary regex, so the check itself can't drift). The diff between the spreadsheet and the database is computed on the **serialized form**, never on typed values (`planilhaValor`, one function, consumed by both export and the import diff) — this is what makes exporting and reimporting the same file unedited close to exactly zero changes (proof by construction, not by luck), and it dissolves the `null` vs `0` fight `correnteNominal` would otherwise have. `lat`/`lon`/`local_id` never appear in the spreadsheet, not even read-only (position is `/mapa` field work, D-03/D-5hy-08). Import never writes before a confirmation screen that names, one by one, every equipment that would be archived (D-5hy-03) — the screen reads worst-to-safest: archive list (or, when blocked, the same list in neutral tone plus the named reason it's blocked), rejected rows, updates, creates, ignored columns/cells. Gate: `tests/refrigeracao-planilha.test.js`.

**Database:** machine tables use the `maq_` prefix; refrigeration tables are unprefixed (`equipamentos`, `arp_itens`, `os_contratacao`, `os_composicao`, …); `usuarios` is shared. Maintenance plans link to assets by `tipo_modelo` (each model has its own manual), not by FK to a specific asset. **Phase 10 (`supabase/25_mapa_geometria_posicao.sql`, additive):** `maq_areas` gains `geom jsonb` (polygon vertices) plus three closed-list terrain attributes (`flora`, `inclinacao`, `limpeza`); `cmasm_locais` and the five asset tables (`maq_ativos`, `transp_ativos`, `elet_ativos`, `fono_ativos`, `equipamentos`) gain nullable `lat`/`lon`, in a deliberate **two-layer position architecture** — position inherited from the building/room in `cmasm_locais`, overridable by a position of the asset's own row — because the existing `local_id` link only places an asset in the org tree, not in space. All twelve position columns share two database-level integrity checks per table: a geographic-envelope check (`-23.2/-22.5/-43.5/-42.7`, one combined `AND` constraint so a swapped lat/lon pair is caught too) and a complete-pair check (never half a coordinate) — both enforced in Postgres regardless of what client-side validation does. **Migration 25 ran in production on 2026-08-18** and was verified against the live database: 16 columns (12 position + `geom` + the three terrain attributes) and 15 checks (6 tables x envelope + complete-pair, plus the three closed lists on `maq_areas`) are in place. What is still untested end-to-end is the **write** path — every position column is `null` and `maq_areas` has zero rows with geometry, so no `salvarZona`/`salvarPosicaoAtivo` call has ever reached the database from the app.

## Dívida de segurança

Herdada de `.planning/BACKLOG-TECNICO.md` (08/08/2026), arquivado em 02/09/2026 —
**54 itens, nenhum marcado**. A lista completa continua lá; o que ela diz, em resumo:

- **A RLS é mais frouxa do que a tela sugere.** O frontend aplica permissão por cargo, mas
  várias policies aceitam escrita de qualquer usuário autenticado, sem distinguir papel —
  é o que faz `podeEditarCadastro()` em `/maquinas` ser explicitamente "UX only". Fechar de
  verdade exige um helper SQL que resolva o papel a partir de `auth.uid()` e `usuarios.auth_id`.
- **As senhas dos cargos seguem no `cmasm2026` inicial**, compartilhadas.
- **O bucket `os-fotos` é público** — precisa virar privado com URL assinada.
- **Concluir OS de Máquinas não é transação:** OS, horímetro, uso, movimento e estoque
  mudam em chamadas independentes; uma falha no meio deixa estado inconsistente. O conserto
  é um RPC transacional que também recuse delta negativo, horímetro regressivo e estoque
  insuficiente.
- **A auditoria é gravada pelo cliente**, logo é alterável por ele; deveria vir de trigger,
  com `auth.uid()`, papel e valores anterior/novo.
- **Certificação pode encerrar OS com divergência** entre orçado, composição, NE e NF, sem
  tolerância definida.
- **`innerHTML` recebe dado do banco sem escape consistente** em `/maquinas`; falta CSP.

Nada disso foi endereçado e nada disso é refinamento — é sistema com dado real da OM.
