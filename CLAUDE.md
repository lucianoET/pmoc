## Commands

There is no build, no npm, no lint, no automated tests. Zero-build static site.

- **Run locally:** open any `index.html` directly in a browser, or `python -m http.server` from the repo root.
- **Deploy:** push to GitHub (`luctronics-ET/pmoc` — this is what `git remote origin` points to and what triggers the deploy; the old `pmoc-overlay` name and the `luctronicserp/pmoc` reference are stale). Vercel serves the repo statically at `https://pmoc-orcin.vercel.app` (`vercel.json` rewrites `/refrigeracao`, `/maquinas`, `/transportes`, `/eletrica`, `/fonoclama`, `/predial`, `/reparos`, `/mapa` and `/calibracao` to their `index.html`; framework "Other", no build command).
- **Database changes:** write a new numbered SQL file in `supabase/` (e.g. `10_*.sql`) and run it in the Supabase SQL editor. Migrations are **additive only — never `DROP`**; archive rows with `ativo = false` instead of deleting.
- **Testing:** manual only, checklist in `TESTES.md`. Verify against the live Supabase data (currently 171 `equipamentos`, 28 `maq_ativos`, 43 `transp_ativos`, etc.). `node --test` runs the automated gate suite (164 tests as of the Reparos module) — no framework, no `package.json`, `node:test`/`node:assert` only. To rehearse the **Máquinas migration chain** (01 → 02 → 09 → 26 → 27) on a throwaway Postgres, use `tests/fixtures/banco-teste-auth.sql`, which stubs the Supabase `auth` schema — `tests/fixtures/banco-teste.sql` is for the *locais* chain and creates `maq_ativos` as a four-column stub. Procedure in `TESTES.md`.
- **Mapa vector floor plan:** `mapa/planta-cmasm.geojson` is generated by running `node mapa/gerar-planta.mjs` by hand against a local `.osm` extract — a one-time, no-network, no-dependency conversion, not a build step. **Mapa raster tiles** (optional, `mapa/tiles/`) have their own user-run procedure in `mapa/tiles/GERAR-TILES.md` (Mapnik/`osmium` rendering chain) — explicitly **not** a deploy step and not required for the map to work offline (the vector floor plan already covers that).

## Architecture

Three independent frontend entry points sharing one Postgres backend via the Supabase JS SDK (v2, loaded from CDN — no imports/bundler):

- `/index.html` — portal (navigation hub)
- `/refrigeracao/index.html` — PMOC Refrigeração v2.8, a **single ~436 KB file** with embedded CSS + JS. HVAC inventory with the full public-contracting workflow: orçamento → execução → fiscalização → composição de pagamento (ARP items) → certificação → auditoria. QR codes, print forms, CSV export (CATMAT).
- `/maquinas/index.html` + `/maquinas/app.js` — PMOC Máquinas v1.0. Hour-meter-based maintenance of cutting equipment: plans per `tipo_modelo`, automatic stock decrement, fuel tracking, depreciation, procurement shopping-list CSV.
- `/reparos/index.html` + `/reparos/app.js` — PMOC Reparos v1.0 (18/08/2026). Symptom → probable-cause catalogue keyed on machine **model** (`rep_modelos`), not on asset or organisation, with the parts (`maq_materiais`) and labour services (`rep_servicos`) each repair consumes. Complements Máquinas: there the trigger is the hour meter (`maq_planos`, deterministic); here it is the reported symptom (probabilistic, ranked). `rep_reparos.frequencia` is incremented by the `rep_confirmar_reparo` RPC when the mechanic confirms the cause while closing a corrective OS in `maquinas/`, so the diagnosis list stops being alphabetical and starts reflecting what actually fails in this workshop. The RPC is `security invoker` and **idempotent** — a second call on the same OS raises instead of double-counting a network retry. Migrations `26_reparos_schema.sql`, `27_reparos_seed.sql` and `28_reparos_alinha_schema.sql`, all applied in production on 2026-08-18 (7 models, 25 services, 33 repairs, all 28 `maq_ativos` back-filled with `modelo_id`). **Migration 28 exists because the `rep_*` tables had been created from a draft schema before 26 ran: `create table if not exists` is a no-op on an existing table, so 26's correct definitions were skipped silently, with no error — additive migrations guarantee a table's existence, not its shape; verify columns after applying.** `maquinas/app.js` loads the catalogue in `carregarCatalogoReparos()`, deliberately **outside** the main `Promise.all`, and only adds `reparo_id`/`sintoma_relatado` to the OS insert when a diagnosis was picked — so on a database without migration 26 the module behaves exactly as it did before. Like `/mapa` after Phase 10, the **write path has never been exercised**: `frequencia` is 0 on all 33 rows; checklist in `TESTES.md`.
- `/shared/auth.js` — reusable role-login ES module (`Auth` class), imported by all six new-generation modules (`transportes`, `eletrica`, `fonoclama`, `predial`, `mapa`, `maquinas`). `refrigeracao` stays outside this base, frozen by user decision.
- `/shared/shell.js` — reusable layout shell (`aplicarShell()`): header, tab strip (when the module has one) and footer, consumed by the same six modules above. Changing `shell.js` changes header/tabs/footer for all six at once.
- `/shared/tema.js` — single light/dark theme implementation (detection, closed-list validation, application, toggling and persistence) for all 7 surfaces (the 6 modules + portal). Consumed by the 6 modules through `aplicarShell()` → `iniciarTema()`, and by the portal directly (it doesn't load the shared shell). Changing it changes the theme mechanism for all 7 surfaces at once. Its two pure functions (`normalizarTema`, `proximoTema`) are deliberately free of any browser API, kept testable in Node — the same pure-core/DOM-applier split `shell.js` already uses between `montarShell()`/`aplicarShell()`.
- `/mapa/` — PMOC Mapa operacional (Phase 10), no longer a demo-data viewer. `mapa/mapa-exportar.js` (GeoJSON out, pure core + DOM edge) and `mapa/mapa-planta.js` (georeferenced reference floor plan, tab-only) are the two files ported in function from the `cmasm-mapa-v2` prototype. `mapa/xmap.js` is the untouched Leaflet component (locked, no edits allowed — see Phase 10 decisions below); `mapa/mapa-dados.js` is the **single door to Supabase** inside `mapa/` — every read and write in the module goes through it (`carregarAreas`, `carregarAtivosDoModulo`, `posicionarAtivos`, `salvarZona`/`atualizarZona`, `salvarPosicaoAtivo`), enforced by a permanent gate (`tests/mapa-camadas.test.js`) so no query is ever allowed to appear anywhere else under `mapa/`; `mapa/mapa-geometria.js` is the pure core (same pure-core/DOM-applier split as `shared/tema.js`) — geodesic area, machine-compatibility rule, closed-list terrain vocabulary, geographic envelope, two-layer position resolution, module deep-link builder — free of any browser API, testable in Node; `mapa/xmap-layers-ativos.js` is the **generic** asset layer — one registration function driven by `CONFIG_POR_MODULO`, not three copies of `xmap-layers-eletrica.js`; `mapa/mapa-editor.js` layers two edit modes (draw a service zone; position/reposition an asset **or building**) on top of the existing map instance, each scoped to the role list that mirrors the write policy of the table it touches; `mapa/planta-cmasm.geojson` is a static vector floor-plan of the CMASM area (117 features, 171 KB, ODbL-attributed, converted once from a local `.osm` extract by `mapa/gerar-planta.mjs`) that draws with the network off; `mapa/tiles/` is the destination for optional local raster tiles (`{z}/{x}/{y}.png`), empty today (only `.gitkeep`), with its own user-run procedure documented in `mapa/tiles/GERAR-TILES.md` — not a deploy step, not a blocker.
- `/calibracao/` — CMASM Controle de Calibração, app legado independente: um único `index.html` de ~860 KB com React 18 e SheetJS **embutidos** (funcionava 100% offline), sidebar e tema próprios, 11 páginas (dashboard, equipamentos, pedidos de serviço, laboratórios, certificados, relatório, lotes, catálogo de preços, saldo da ATA, dados, ajuda). **Migrado do localStorage para o Supabase em 18/08/2026** (migrações 35 e 36): era o único módulo da plataforma sem banco — os 38 instrumentos, 8 laboratórios, 12 PS, 2 lotes e o catálogo viviam em `localStorage['cmasm_erp_state_v1']`, de modo que limpar o cache apagava o controle de calibração e cada computador via um dado diferente. `useStore()` continua sendo a **costura única**: carrega as cinco tabelas `cal_*` em paralelo e cada mutator grava a própria linha — nunca o blob, senão dois usuários simultâneos se sobrescrevem em silêncio. Fora de `useStore()` e dos helpers de borda o React é intocado, e por isso a gravação é **otimista** (a tela já mostrou a mudança; erro alerta e recarrega): tornar os mutators assíncronos obrigaria a reescrever as 11 páginas. Duas fronteiras, cada uma num lugar só: `CAMPOS_LAB`/`CAMPOS_EQ`/`CAMPOS_PS`/`CAMPOS_LOTE` traduzem o camelCase do app (`eqId`, `labId`, `cC`) para o snake_case do Postgres, e `paraISO`/`paraBR` traduzem `dd/mm/aaaa` para `date` — o gate compara os mapas coluna a coluna com a migração 35, porque **um campo fora do mapa é gravado como null sem erro nenhum**. O contador de PS deixou de ser persistido: é derivado do maior `PS-CMS-{ano}-NNN` já emitido, e `cal_ps.num` é `unique`, porque um número de sequência mantido no cliente produz PS duplicado assim que duas pessoas emitem ao mesmo tempo. `ATA_ITEMS_SEED` (35 itens da ata 00129/2025) e `ATA_INFO` **não ganharam tabela** — conferido que só aparecem em `.map()`/`.find()`, nunca em escrita. O SDK do Supabase vem de CDN, ao contrário do React e do SheetJS embutidos: o módulo passou a depender de rede de qualquer forma, então embutir o SDK não devolveria o modo offline. `calibracao/gerar-seed.mjs` gera a migração 36 a partir das constantes do próprio `index.html`, rodado à mão uma vez, como `mapa/gerar-planta.mjs` — não é passo de build. Gate: `tests/calibracao-supabase.test.js`.

**Cobertura e posicionamento do mapa (quick-260818-vxu, 18/08/2026):** the map covered 2 of the 5 asset families — 229 assets (43 `transp_ativos`, 15 `fono_ativos`, 171 `equipamentos`) had a `lat`/`lon` pair from migration 25 and no layer to appear in. `mapa/mapa-dados.js` replaced `TABELA_POR_MODULO`/`COLUNAS_POR_MODULO` with a single **`CONFIG_POR_MODULO`** because `equipamentos` shares *no* column with the other four: no `ativo`, no `codigo`, no `nome`, no `status` — its state lives in `funciona` (`OK`/`NOK`) while the column literally named `estado` holds the unit's age (`NOVA`/`SEMI`/`VELHA`). With fixed columns the only way in was an `if` for one module inside the loader, and the next odd schema would bring the second; the table's shape is now data. The module key is **`climatizacao`, never `refrigeracao`** — `tests/mobile-375.test.js` (PLAT-15) forbids naming the frozen app in `mapa/index.html`, and `MODULOS` (`mapa-geometria.js`) has no route for it, so the popup simply omits the ficha link. **Two position doors, one per layer of `resolverPosicao`:** `salvarPosicaoAtivo` (asset's own row, forbidden from touching `cmasm_locais`, D-03) and the new `salvarPosicaoLocal` (`cmasm_locais` only, touching no asset table) — the `if` choosing between them lives in the *caller* (`aoClicarParaPosicionar`), so neither function ever decides on its own which table to write. Until this task the inherited layer was dead code: there was no way to give a building a coordinate. The sidebar lists buildings **ordered by how many assets each one would light up** (counted from `NAO_LOCALIZADOS`, no extra query — an asset is only in that list if it has neither its own nor an inherited position, so its `local_id` names exactly the building that would place it), truncated at 25 with the remainder **announced**, never silently. Zones with `geom` null were unreachable (`carregarZonasEditaveis` skips fewer than 3 vertices) and drawing over one inserted a duplicate; the "Desenhar" button now **arms** the next polygon for `atualizarZona` of that row. Estado vocabulary moved into the pure core (`ESTADOS`, `normalizarEstado`, `corDoEstado`, `rotuloDoEstado`, `classeDoEstado`): three duplicated bridges plus their palettes became one closed list that both the markers and the legend read — `sobreaviso` (`transp_ativos`) got its own state (`standby`) rather than being folded into operante or manutenção. The map now opens with the 5 real-data layers on; **aguada stays off**, it is the only one still showing demo data (D-01). **A gate had gone blind:** `tests/mapa-editor.test.js` asserted the table inventory by scanning literal `.from('...')`, and kept passing after the names moved into `CONFIG_POR_MODULO` — validating only 2 of 7 tables. It now reads both sources. Gate: `tests/mapa-cobertura.test.js` (the estado vocabulary is tested by *behaviour*, importing the pure core in Node, not by regex over the file).

**Prédio como polígono, zona como vegetação, controles do mapa (quick-260819-0g3, 19/08/2026):** a building was a **point** and the database showed what that cost — two of the seven zones the user had drawn in `maq_areas` were buildings ("Predio Comando", "Museu"), drawn with the service-zone tool because it was the only drawing tool that existed, which also put 2.253 m² of headquarters into the grass-cutting area. `cmasm_locais.geom` (migration 37, additive, **applied in production on 2026-08-19** and verified: column plus a shape `check`, since a brand-new column can be constrained without invalidating any existing row — `maq_areas.geom` never got that guard) holds the outline in the same `[[lat,lon], …]` shape. **`lat`/`lon` did not become optional:** `salvarGeomLocal` writes the outline and its **centroid in the same `.update(`**, because `resolverPosicao` reads the point, not the polygon — an outline without a point would silently stop lighting up every asset that inherits from that building, and that half-written state would be invisible on screen (the outline would draw, the assets would vanish). The centroid is an **area** centroid, not a vertex mean: a detailed façade with many vertices would drag a mean outside the floor plan. Two numeric corrections the test itself found: the shoelace runs with the first vertex at the origin (subtracting near-equal products at −22,84/−43,10 left noise of the same order as the building's area) and degeneracy is compared against an epsilon, never against exact zero (three collinear vertices leave a 1e-17 remainder, and the "centroid" would be noise over noise). Drawing a building is `CARGOS_POSICAO` — the list that already governed `cmasm_locais` — **not** `CARGOS_ZONA`, which mirrors `maq_areas`'s policy and has nothing to do with this write; it uses `new L.Draw.Polygon(mapa).enable()` directly, adding no toolbar to the map. Zones are now **vegetation and outdoor areas**, coloured by `flora` (the closed list of migration 25) instead of the legacy cmms-mapa dictionary (jardim/bosque/canteiro/área recreativa/horta), a vocabulary that never existed in this database — none of the seven real zones matched a key, so every one fell to the default green and the style-by-type was decorative. **Three real control overlaps, all fixed in the module's own CSS (`mapa/xmap.js` and `mapa/xmap.css` untouched):** "Editar zonas"/"Mover ativos" were Leaflet controls in `topright` — the same corner as the `.xmap-filters` panel (z-index 1000) and *below* it in the stack, so two buttons were invisible; they moved to the sidebar (`#edicao-controles`), and entering a mode now closes the sidebar instead of covering half the map you are about to click. The Layers panel also covered `#editor-painel` (z-index 900) and now steps aside while it is open, scrolling inside itself rather than growing to the footer. The basemap bar left the top centre, where it collided with ☰ Módulos on a narrow screen, for the bottom-left corner freed by hiding the active-module chips (they repeated the sidebar). **Sala herda a posição do prédio (quick-260819-23e, 19/08/2026):** positioning buildings lit up **nothing**, and the database said why: **175 of the 190 assets point at a `sala`**, and inheritance looked only at the asset's direct `local_id`. The 132 active salas are *all* children of an `edificacao` — the tree is exactly two levels deep (sala → prédio → OM). Inheritance now climbs `parent_id`: `localAscendente` (pure core) walks up with a **cycle guard**, because `parent_id` carries no acyclicity constraint in Postgres and a circular registry would freeze the tab with no error at all. Two climbs, two criteria: `localComPosicao` (where the coordinate comes from) and `localPosicionavel` (which local the user should position to light this asset up — the sala hands off to its prédio), which is what makes the sidebar's per-building count tell the truth. `carregarLocaisComPosicao` became **`carregarArvoreDeLocais`** and stopped filtering on `lat is not null`: the middle link — the sala, which never has a coordinate — must come back, or the chain breaks exactly where it needed to climb. `sala` left the "position me" list (`TIPOS_QUE_HERDAM_POSICAO`, a closed list of what *inherits*, deliberately inverted so an unknown new tipo shows up on screen instead of vanishing from it). **The root's coordinate is not inheritable** (`TIPOS_SEM_HERANCA = ['organizacao militar']`): the CMASM row itself has `lat`/`lon`, so an unbounded climb would have positioned every asset in the base — 188 pins stacked on one point, the map claiming "all located" and the não-localizados list, which *is* the field-work backlog, emptying itself. A point at the centre of 20 hectares is the absence of a position wearing the costume of data. Popups now name the origin ("Herdada de COMANDO") instead of just "herdada"; `xmap-layers-ativos.js` gained the `esc()` it never had. Measured against the live database: **54 assets positioned (16 own + 38 inherited) against 39 before**, with F21 lighting up 19 assets, PAIOL 16, MK48 12. Gate: `tests/mapa-heranca-posicao.test.js`.

**Legibilidade do mapa: pilha de marcadores, rótulos, barra lateral, painel de camadas (quick-260819-348, 19/08/2026):** with the 30 buildings positioned, the screen measured **195 markers over 51 distinct points** — the tallest stack 24 icons on the same pixel (F21 19, PAIOL 16, MK48 12) — and **12 labels, all from the OSM floor plan, none from the cadastre**. The layer toggles *worked* (turning Climatização off removed 171 markers); what did not work was seeing it. Four causes, four fixes. **`agruparPorPonto`** (pure core) groups by **exact** coordinate, because the stack comes from identical coordinates — every asset inherits its building's point — not from proximity; a proximity cluster library would move the marker somewhere it isn't, which on a maintenance map is worse than stacking. **`mapa/xmap-marcadores.js`** is one marker implementation for the three asset layers: what varies is the single-asset icon and its popup, while grouping, the count badge, the colour, the list popup and the label are shared — a fix in one of three copies would never have reached the other two. The group takes the colour of its **most severe** state (`inoperante` > `manutencao` > `standby` > `operante` > `baixado`): one broken unit among twenty working ones has to be visible from far away, and an average or majority would hide exactly what the screen exists to show; an unknown state weighs as least severe rather than faking severity. The group popup **lists** its assets, each line linking to the asset's ficha, cut at 15 with the remainder announced — grouping must not cost access to the asset. **Labels are permanent tooltips hidden by CSS below zoom 17** (`.leaflet-container:not(.zoom-detalhe) .xmap-rotulo`), one class toggled on the container by `app.js` instead of every layer listening to the map. The sidebar became collapsible `<details>` sections — seven simultaneously open blocks were a wall of text — with only *Módulos* and *Edição* open and each closed header carrying its own count. The Layers panel now **starts collapsed** behind its own Portuguese header (`#btn-camadas`), placed *outside* the panel because `xmap.js` rebuilds the panel's entire interior on every toggle and would erase anything put inside it. The map opens **framing what has a position**, with `animate: false`: Leaflet's animation runs in `requestAnimationFrame`, which does not fire while the tab is not compositing, so the animated `fitBounds` silently did nothing and the map opened at zoom 15 with the base the size of a fingernail. After: **56 markers, 66 labels, zoom 17**. `mapa/xmap.js` and `mapa/xmap.css` still untouched. Gate: `tests/mapa-legibilidade.test.js`.

**Features portadas do cmasm-mapa-v2 (quick-260819-406, 19/08/2026):** `/home/luc/DEV_reference_readonly/cmasm-mapa-v2 (2).html` is a MapLibre GL + mapbox-gl-draw prototype; `/mapa` is Leaflet with `xmap.js` locked, so what gets ported is **function, not code** — and one of them comes out better than the original. **`mapa/mapa-exportar.js`** exports positioned assets, zones and building outlines as GeoJSON from what is already in memory (no new query). Its core is the coordinate order: `geom` stores `[lat, lon]` (Leaflet's order) and RFC 7946 demands `[lon, lat]` — exporting them swapped raises no error anywhere, it just puts the CMASM in Antarctica when the file opens in QGIS, which is why that is the one thing tested by behaviour. The polygon ring is **closed on export** because Leaflet's drawing does not repeat the first vertex. **`mapa/mapa-planta.js`** is the reference floor plan: the original is an `<img>` positioned with a CSS `transform`, so it does **not** follow the map — pan and the plan stays put, which makes it useful to look at but useless to draw over. Here it is `L.imageOverlay` bound to coordinates, georeferenced by hand ("Encaixar aqui" snaps it to the current view), living in the tab only — persisting it would need a Storage bucket with its own policy. The **toast** exists for a concrete reason: the editor instructed with `alert()`, and `alert` is modal — it swallowed exactly the map click the instruction was asking for; errors and validation stay in `alert`, the project idiom, because an error must stop the user. Layer **opacity is one global slider** acting on `overlayPane`/`markerPane`/`tooltipPane` and never on `tilePane` (the point is seeing the ground *under* the data); per-layer would mean editing the panel `xmap.js` rebuilds on every toggle. Live coordinate readout plus metric scale complete the set. **Deliberately not ported:** the TOPO basemap (the basemap list lives in the locked `xmap.js`), map rotation and 3D pitch (Leaflet 1.9 does neither — it would mean replacing the component with MapLibre, the rewrite the xMap port avoided), the symbol palette that inserts free-standing elements (a pmoc asset comes from one of the five tables; an element that exists only on the map has no registry, no OS and no owner), the properties panel / element list / 3D modal (equivalents already exist; the reference's 3D modal is an empty placeholder), and the Delete shortcut (the project archives, never deletes). Gate: `tests/mapa-referencia-v2.test.js`.

**Theme convention (locked, Phase 6):** `data-theme="claro"|"escuro"` attribute on the root element, `localStorage` key `pmoc-tema` (values in Portuguese, matching the rest of the codebase). Dark stays the default in `shared/pmoc.css:root` (unchanged, byte-identical); light is an additive `[data-theme="claro"]` block overriding only the neutral/semantic tokens. Three deliberate exceptions: the portal duplicates the same token *values* inline (it never loads `shared/pmoc.css`) but reuses `shared/tema.js` for all logic — no theme code is duplicated; `mapa/xmap.css` (the Leaflet skin, its own `--xm-*` token system) stays dark-only by decision, out of scope; and `/calibracao` (D-05) is a standalone legacy app outside this convention entirely — it ships its own toggle on `localStorage['cmasm_erp_theme']` with `dark`/`light` values, so switching the platform theme does not affect it. `refrigeracao` is outside as well, frozen (D-04). A classic (non-module, no external `src`) anti-FOUC script — inline, byte-identical — is replicated in the `<head>` of all 7 surfaces, immediately after the `theme-color` meta tag, applying the saved/detected theme before first paint; ES modules are deferred and would repaint too late, reintroducing the flash. `tests/tema-superficies.test.js` enforces that the 7 copies stay identical — don't fix one and forget the other six.

**State pattern (both apps):** global UPPER_CASE arrays (`ATIVOS`, `OS_LIST`, `MATERIAIS`, `PLANOS`, …) populated by `carregarTudo()` (parallel `Promise.all` Supabase queries), then `render*()` functions rebuild DOM sections via template literals. Every save re-runs `carregarTudo()` — no optimistic updates, no partial refresh. Modals drive all CRUD; inline `onclick="fn(${id})"` handlers are the norm.

**Auth & security:** login is by cargo button + password — emails (`direcao@cmasm.local`, etc.) are internal and never shown to users. Roles: `admin`, `gestor`, `tecnico`, `observador` (read-only, no password). Role lives in the `usuarios` table. The Supabase `anon key` is hardcoded in the frontends **by design** — real access control is RLS policies in Postgres; any client-side permission check is UX only. New cargos: edit the `CARGOS` array at the top of `maquinas/app.js`. `mapa/mapa-dados.js` exports **two separate role lists**, deliberately different, because each screen mirrors the write policy of the table it grants — not a UI preference: `CARGOS_ZONA` (`admin`, `gestor`, defined in `mapa/mapa-editor.js`) mirrors `maq_areas`'s write policy 1:1 (migration 12, `role in ('admin','gestor')`); `CARGOS_POSICAO` (`admin`, `gestor`, `tecnico`, exported from `mapa/mapa-dados.js`) is a **deliberate subset** of what the asset tables' policy would actually accept (`to authenticated using (true)`, no `role in (...)` restriction) — the client list is narrower than the database would allow, by design, not a mirror. A permanent test compares each list against the real policy it claims to reflect (`tests/mapa-editor.test.js`, `tests/mapa-posicionamento.test.js`).

**OS lifecycle (Máquinas, 18/08/2026):** `maq_os.status` always accepted the closed list `pendente`/`em_andamento`/`concluida`/`cancelada` (migration 01), but the app hardcoded `'concluida'` on insert — every OS was born finished, and stock was debited at creation time. The workshop flow (18/08/2026, evening) is **Aberta (reception) → Delineamento (diagnosis; parts+services listed; `delineado_por`/`delineado_em` recorded on closing it) → Espera (waiting for parts or a technician) → Em execução → Concluída** — `supabase/31_maquinas_os_fluxo.sql` (**applied in production on 2026-08-18** and verified against the live database: the check accepts all 6 states, both delineation columns exist, and the 4 pre-existing OS — all `concluida` — remain valid under the new constraint) widened the `maq_os_status_check` closed list with the two new states (first constraint *swap* in the project — nothing dropped, the list only grows) and added the two delineation columns. **Stock is debited when execution STARTS, never on creation or waiting** — an OS on the shelf that already consumed a part would lie about the inventory. Every path into execution (advance from the list, create-as-executing, status change in the detail modal, concluding an old OS that never executed) calls the same `baixarPecasDaOS()`, which is **idempotent**: it checks `maq_estoque_movimentos` for an existing 'saida' with that `os_id` — the stock's own record, not a parallel flag — so concluding an OS whose parts already left the shelf does not debit twice. The OS list has a **Material** column (⚠ falta N / EM ESTOQUE) plus a `filtro-os` select whose `falta` option isolates OS blocked on parts (`faltasDaOS()` — meaningless once execution started, so it returns empty then). `supabase/29_maquinas_os_itens.sql` (additive, **applied in production on 2026-08-18** and verified against the live database: 8 columns, the `(os_id, plano_id)` unique, both indexes, RLS on with its two policies, `maq_os` untouched) adds `maq_os_itens` so one OS can carry several maintenance items — `maq_os.plano_id` stays populated with the first item, so nothing written before it breaks. `carregarItensOS()` sits **outside** the main `Promise.all` for the same reason `carregarCatalogoReparos()` does: without migration 29 the list stays empty and `itensDaOS()` falls back to the single `plano_id`, exactly as the module behaved before. Gate: `tests/os-ciclo-vida-maquinas.test.js`.

**OS costs (Máquinas, 18/08/2026):** `maq_os.custo_pecas` and `custo_mo` used to be numbers typed into the form — nobody knew which parts or how many hours produced them. `supabase/30_maquinas_os_custos.sql` (additive, **applied in production on 2026-08-18** and verified against the live database: all three tables with the exact shape, 7 constraints on `maq_os_materiais` including the `(os_id, material_id)` unique, 6 on `maq_os_servicos` including the identification check, RLS on all three with its 6 policies, `valor_hora_padrao` still null) adds `maq_os_materiais` and `maq_os_servicos` (the two lists an OS carries) plus `maq_config` (one row per key; today only `valor_hora_padrao`). Cost is now derived: parts = Σ quantity × unit price, labour = Σ hours × hourly rate, and both fields are read-only on screen. **Unit values are frozen on the row** (`preco_unit`, `valor_hora`), not just referenced — a catalogue reprice in September must not change an OS closed in August; the FK says where it came from, the value column says what it cost. `pecasPrevistasDaOS()` merges plan and diagnosis into **one** list keyed by material, so a part appearing in both is debited once, not twice; `baixarPecasDaOS(osId, pecas, reparo)` takes that resolved list. Concluding an OS debits its own `maq_os_materiais` rows, falling back to the resolved prediction only for OS created before migration 30. OS part lines are **consolidated by material before insert** (`consolidarPecas` — the DB unique `(os_id, material_id)` would reject duplicates; picking an already-listed part merges into the existing line), new lines are born unselected, and both OS selects carry a "➕ Cadastrar novo…" option that opens the quick-create modal and returns the new item to the requesting line. `maq_materiais.servico_id` (migration 33, **applied in production on 2026-08-18**; column+FK verified, 0/34 materials linked so far — links are filled part by part in the stock register) links a part to its default service: picking the part adds the service to the OS and picking the service pulls its parts — both directions from one column, managed in the material modal (which now also edits). The hourly rate is **a single module-wide value, deliberately empty** — inventing one would produce false labour cost on every OS; while empty, labour is zero and the screen says why. Gate: `tests/os-custos-maquinas.test.js`.

**Ficha da máquina (Máquinas, 18/08/2026):** clicking a machine row opens a **consultation card** (`abrirFichaAtivo`), not the edit form. Identity fields (código, nome, categoria, fabricante, modelo, patrimônio) are display-only — they don't change day to day — and `uso_atual` is **calculated from use records**: the field is disabled when editing an existing machine and only accepted as the initial reading on creation (`salvarAtivo` includes it in the payload only for inserts). Daily actions live on the card: Registrar uso, Abrir OS, comments (`maq_ativo_comentarios`, migration 32, dated+signed log), plus instructions (`maq_ativos.instrucoes`), scheduled operations and the last 5 OS/use records. "Editar cadastro" is gated to admin/gestor — fixing a typo in the registry is an exception, not routine. Machine photos were deliberately deferred: they need a Supabase Storage bucket with its own policies. Migration `32_maquinas_ficha.sql` **applied in production on 2026-08-18** and verified against the live database (5 columns, non-empty-text check, cascade FK, the `(ativo_id, criado_em desc)` index, RLS with both policies, `maq_ativos.instrucoes` in place). Gate: `tests/ficha-ativo-maquinas.test.js`.

**Necessidades e listas de compra (Máquinas, 18/08/2026):** the "Lista de compras" tab was a photograph — it showed what was missing but nobody could say "this has already been ordered" nor book in what arrived, and the whole thing evaporated on reload. It is now **Necessidades** (`view-necessidades`, `navItems` id `necessidades`), a process. Need per material is computed by a locked formula: `bruto = max(preventiva + corretiva, estoque_minimo − estoque_atual)` — replenishing the minimum is a **floor, not a summed term**, otherwise the same part is counted twice — and `a_comprar = max(0, bruto − estoque_atual − aquisicao)`. `preventiva` comes from `calcVencimentos()` at `pct >= 70` via `maq_plano_materiais`; `corretiva` from `pecasParaBaixa()` over OS not yet executed (`OS_NAO_EXECUTADA = ['pendente','delineamento','espera']` — the three states before stock is debited at execution start). Selecting rows generates a purchase list (BOM: título, descrição, data) in `maq_compras_listas`/`maq_compras_itens`; **unit price is frozen on the line** (`preco_unit`), same reason already recorded in migration 30. **`aquisicao` is deliberately NOT a stored column** — it is derived as `Σ(quantidade − qtd_recebida)` over items in `aberta`/`enviada` lists, because a denormalized column drifts from what was actually received. Receiving is item-by-item (`receberItem`): it raises `qtd_recebida`, writes an `entrada` row in `maq_estoque_movimentos`, increments `maq_materiais.estoque_atual`, refuses more than the outstanding quantity, and flips the list to `recebida` on its own when the last item lands. `maq_materiais` also gains `sistema` (free text, datalist-suggested) and `aplicacao` (which models use the part, with a fixed **"Vários"** option) — both free text, not FK, because a legitimate new part can name a model nobody has registered yet. The hourly rate left the Estoque tab for `modal-hora-homem`, opened from the OS tab header where labour cost is actually consumed. Migration `34_maquinas_compras_necessidades.sql` **applied in production on 2026-08-18** and verified against the live database (17 columns, 9 constraints, 4 indexes, RLS on both tables with two policies each), with the full path exercised against real data — need → list → partial receipt → final receipt → list closes itself — and the test rows removed afterwards. Like `carregarCatalogoReparos()` and `carregarItensOS()`, `carregarCompras()` sits **outside** the main `Promise.all`: on a database without migration 34 the tab behaves exactly as it did before, no selection, no lists, no error (verified before applying). Gate: `tests/necessidades-compras-maquinas.test.js`.

**Tabela do Estoque — cadastro, ordenação e filtro (Máquinas, 18/08/2026):** editing a material's registry used to be reachable only by clicking its *name* — an affordance discovered on hover, and open to `tecnico`. It is now an explicit `⚙` button in the row's action cell, gated by `podeEditarCadastro()` (`admin`, `gestor`), the **same helper** that gates "Editar cadastro" on the machine card — one list of roles, four call sites (name link, `⚙`, the edit branch of `salvarMaterial()`, the ficha button). The `✎` button next to it is untouched: inline edit of estoque atual / mínimo / preço stays on `podeEscreverNoModulo()` (`admin`, `gestor`, `tecnico`) because it is the technician's daily action. Creating a material (`+ Material`) is likewise unchanged. **This gate is UX only** — `maq_materiais`'s policy scopes writes to `authenticated` without distinguishing cargo, so closing it for real would need a migration; the screen simply stops offering what it says it doesn't offer. Each `<th>` of `#tb-materiais` carries a sort button (`⇅` → `↑` → `↓` → `⇅`, one column at a time, `aria-sort` on the th) and a filter icon (`⌕`) that opens a filter row and focuses that column's field — substring match, accent- and case-insensitive, filters combine. `maquinas/estoque-tabela.js` is the **pure core** (`COLUNAS_ESTOQUE`, `proximaOrdem`, `normalizarBusca`, `compararMateriais`, `aplicarOrdemEFiltro`) with no browser API, same pure-core/DOM-applier split as `shared/tema.js` and `mapa/mapa-geometria.js`, so the gate tests real ordering behaviour (numeric vs. `localeCompare('pt-BR')`, empty values always last in **both** directions) instead of regexing markup. `renderMateriais()` split into `renderCabecalhoMateriais()` + `renderLinhasMateriais()` for one concrete reason: redrawing the header on every keystroke would kill the filter field's focus and cursor — typing repaints the body only. Sorting and filtering are **screen state**, never a re-query: no Supabase call, no `carregarTudo()`. A row being inline-edited that falls out of the filter has its edit cancelled rather than vanishing with filled fields. Scope is the Estoque table alone — not generalized to the OS, Máquinas or Necessidades tables. Gate: `tests/estoque-cabecalho-maquinas.test.js`.

**Tabelas do /reparos — edição, ordenação, densidade e tipo de máquina (18/08/2026):** the three catalogue tables (Reparos, Serviços, Modelos) were read-only — the modals only ever inserted, and only the Diagnóstico view had filters. Each row now carries a `⚙` that reopens its own modal in edit mode (`abrirModalReparo(id)` etc.; `salvar*()` branches to update when an id is being edited), gated by the role that already governs that table — `podeCatalogo()` for modelos/serviços, `podeConhecimento()` for reparos. Unlike the Estoque gate, **this one is not UX-only**: migration 26 scopes writes on `rep_modelos`/`rep_servicos` to admin+gestor and on `rep_reparos` to admin+gestor+técnico, so Postgres refuses too. Inline row editing was rejected: sintoma, causa provável and procedimento are long texts that don't fit a cell — the Estoque's inline edit works because it is three numbers. The `⚙` on a Reparos row calls `event.stopPropagation()` because the row itself already opens the parts/services modal. The sort/filter core the Estoque grew is now generic in **`shared/tabela.js`**, driven by a column definition passed in; `maquinas/estoque-tabela.js` keeps only `COLUNAS_ESTOQUE` plus a thin adapter, so `tests/estoque-cabecalho-maquinas.test.js` passed **without a line changed** — the gate is contract, not draft. `reparos/tabelas.js` holds the three column definitions plus pure display-row builders (the columns read a resolved view model, never the globals, which is what keeps it testable in Node). Columns were collapsed to what is read together: Reparos 8→5 (código+modelo, sintoma→causa, sistema+gravidade), Serviços 6→4 (código+nome, tempo+valor-hora), Modelos 7→4 (código+fabricante modelo, máquinas+reparos); mixed cells sort by their principal datum, never by concatenated text. Compact CSS is scoped to `reparos/index.html` — `.tbl` in `shared/pmoc.css` is untouched because six modules depend on it. A single `<select>` with two `<optgroup>` — **Tipo** (the distinct `rep_modelos.categoria`: roçadeira, motosserra, minitrator, trator) and **Modelo** (fabricante + modelo, which is where "Tobata CT151" lives, since Tobata is a manufacturer and not a category) — filters all three tabs, plus an "Agrupar por tipo" toggle that inserts counted group headers. A repair with no `modelo_id` is **never filtered out** (it applies to any machine), the rule `reparosFiltrados()` already used. A service used by more than one category groups under "Vários tipos" rather than being duplicated across groups, which would lie in the counts. Peças stayed out of scope on purpose: a part is `maq_materiais`, from the Máquinas module, and filtering parts by machine type is **already possible** through the `Aplicação` column filter on the Estoque table. Gates: `tests/tabela-compartilhada.test.js`, `tests/reparos-tabelas.test.js`.

**Database:** machine tables use the `maq_` prefix; refrigeration tables are unprefixed (`equipamentos`, `arp_itens`, `os_contratacao`, `os_composicao`, …); `usuarios` is shared. Maintenance plans link to assets by `tipo_modelo` (each model has its own manual), not by FK to a specific asset. **Phase 10 (`supabase/25_mapa_geometria_posicao.sql`, additive):** `maq_areas` gains `geom jsonb` (polygon vertices) plus three closed-list terrain attributes (`flora`, `inclinacao`, `limpeza`); `cmasm_locais` and the five asset tables (`maq_ativos`, `transp_ativos`, `elet_ativos`, `fono_ativos`, `equipamentos`) gain nullable `lat`/`lon`, in a deliberate **two-layer position architecture** — position inherited from the building/room in `cmasm_locais`, overridable by a position of the asset's own row — because the existing `local_id` link only places an asset in the org tree, not in space. All twelve position columns share two database-level integrity checks per table: a geographic-envelope check (`-23.2/-22.5/-43.5/-42.7`, one combined `AND` constraint so a swapped lat/lon pair is caught too) and a complete-pair check (never half a coordinate) — both enforced in Postgres regardless of what client-side validation does. **Migration 25 ran in production on 2026-08-18** and was verified against the live database: 16 columns (12 position + `geom` + the three terrain attributes) and 15 checks (6 tables x envelope + complete-pair, plus the three closed lists on `maq_areas`) are in place. What is still untested end-to-end is the **write** path — every position column is `null` and `maq_areas` has zero rows with geometry, so no `salvarZona`/`salvarPosicaoAtivo` call has ever reached the database from the app.

## Conventions

- Globals `UPPER_CASE`, functions `camelCase`, private helpers `_prefixed`, HTML ids `kebab-case`.
- Section comments as `// ── nome ──`.
- Supabase error handling idiom: `const { error } = await supa.from(...)…; if(error){ alert('Erro: '+error.message); return }`.
- Detailed codebase analysis lives in `.planning/codebase/` (ARCHITECTURE, STACK, CONVENTIONS, TESTING, CONCERNS, INTEGRATIONS, STRUCTURE) — read those before large changes.

## Decisões travadas — Phase 10 (mapa operacional)

Each has a permanent automated gate — a future phase contradicting one of these fails `node --test` before reaching human review:

- **D-01** — the `aguada` layer stays **out** of the "camadas leem do Supabase" requirement (PLAT-17), deferred to Phase 11. It has no table in pmoc — it's an autonomous external system (FastAPI + SQLite, fed by MQTT). Gate: `tests/mapa-decisoes.test.js`.
- **D-02** — the satellite basemap stays **online-only**, no local tile cache, by user decision. Gate: `tests/mapa-base-offline.test.js` (scoped to the satellite construction region of `mapa/xmap.js`, not the whole file, because the local-tile class legitimately appears elsewhere in the same file for the other basemap).
- **D-03** — service zones live in `maq_areas`, deliberately **outside** the `cmasm_locais` tree — they're auxiliary and temporary, not permanent locations. Not gated by a dedicated test; documented here so a future phase doesn't "reorganize" them into the locations tree.
- **D-04** — time/cost estimate per zone is **out of scope**. Not in the legacy app; when it arrives, it should derive from real execution (`maq_operacoes.horas_utilizadas`/`area_executada_m2`), not an arbitrary constant. Gate: `tests/mapa-decisoes.test.js` (no file under `mapa/` may reference those two columns).
